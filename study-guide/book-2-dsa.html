1 · Big-O & Complexity Analysis

What

Big-O describes how an algorithm's cost grows as the input grows — it ignores constants and small terms to capture the shape of the curve. O(1) is constant, O(log n) halving, O(n) linear, O(n log n) good sorts, O(n²) nested loops, O(2ⁿ) combinatorial. You analyze both time and space.

Why it matters

Because it's the language of every design decision. "Is this fast enough?" is unanswerable without knowing how it scales. A choice that's fine at 100 items (O(n²)) melts down at 1,000,000. Big-O is how you predict that before shipping — and how interviewers probe whether you can.

How — reading complexity off code
# O(1) — no loop over the input
first = items[0]

# O(n) — one pass
for x in items: total += x

# O(n²) — nested pass over the same input
for a in items:
    for b in items: compare(a, b)

# O(log n) — the search space HALVES each step
while lo <= hi:
    mid = (lo + hi) // 2       # binary search
🔎
Amortized ≠ per-call

Appending to a Python list is amortized O(1): most appends are instant, but occasionally the list doubles its backing array (an O(n) copy). Spread over many appends the average is constant. "Amortized" means "averaged over a sequence of operations" — a distinct idea from average-case (averaged over inputs).

⚠️
Gotcha — hidden costs in one-liners

if x in my_list looks O(1) but is O(n) — it scans. list.insert(0, x) is O(n) (shifts everything). String concatenation in a loop is O(n²). The elegant line can hide the quadratic; know your containers' Big-O cold.

Q · What's the difference between average-case and amortized complexity?

Average-case averages over the distribution of inputs (e.g., quicksort is O(n log n) on average). Amortized averages the cost of one operation over a sequence of operations on the same structure (e.g., dynamic-array append is O(1) amortized because the rare O(n) resize is paid back by many cheap appends).

Q · Why do we drop constants and lower-order terms?

Big-O captures growth, not exact runtime. As n → ∞ the highest-order term dominates and machine-specific constants become noise. 3n² + 100n + 5 is O(n²) because for large n the n² term swamps the rest.

2 · Arrays, Linked Lists & Dynamic Arrays

What

An array stores elements in one contiguous block — index access is O(1) arithmetic. A linked list stores each element in its own node with a pointer to the next — no contiguity, so O(1) insert/delete at a known node but O(n) to reach it. Python's list is a dynamic array: contiguous, but it grows by reallocating.

Why it matters

This is the first real trade-off in the book: fast random access vs fast middle-insertion. Pick wrong and a hot loop turns quadratic. It also teaches cache locality — contiguous arrays are dramatically faster in practice than pointer-chasing lists, even at the same Big-O.

🔎
Why append is amortized O(1)

A dynamic array over-allocates: when it fills, it copies into a new block ~2× as big. That copy is O(n), but it happens rarely enough that the total cost of n appends is O(n) — so O(1) each on average. This is the canonical amortized-analysis example.

Q · When is a linked list actually the right choice?

When you do many insertions/deletions at positions you already hold a reference to (e.g., an LRU cache's recency list, or a queue), and you don't need random access. In practice, arrays win most of the time due to cache locality — so reach for a linked structure only when the O(1) splice genuinely dominates your workload.

3 · Stacks, Queues & Deques

What

Restricted-access sequences defined by where you add/remove. A stack is LIFO (last-in, first-out) — push/pop at one end. A queue is FIFO (first-in, first-out) — enqueue at the back, dequeue at the front. A deque ("deck") allows O(1) at both ends.

Why it matters

Because the access discipline is the algorithm. A stack is the call stack, undo history, expression parsing, and DFS. A queue is BFS, task scheduling, and buffering. Choosing the right one makes the solution fall out naturally.

How
from collections import deque

stack = []                    # a list makes a fine stack
stack.append(1); stack.pop()    # push / pop — both O(1) at the end

queue = deque()               # NEVER use list.pop(0) — that's O(n)
queue.append(1)              # enqueue at back — O(1)
queue.popleft()               # dequeue at front — O(1)
⚠️
Gotcha — list.pop(0) is O(n)

Using a plain list as a queue and calling pop(0) shifts every remaining element left — O(n) per dequeue, O(n²) overall. Use collections.deque, whose popleft() is O(1). This single mistake quietly turns a linear algorithm quadratic.

Q · Stack vs queue — give a real use for each.

Stack (LIFO): the function call stack, undo/redo, balanced-parenthesis checking, and depth-first search. Queue (FIFO): breadth-first search, print/task scheduling, and rate-limiting buffers. If order of processing must match order of arrival, it's a queue; if you want to revisit the most recent thing first, it's a stack.

4 · Hash Tables — How dict Really Works

What

A hash table gives average O(1) lookup by running the key through a hash function to get an array index. Two keys can map to the same slot — a collision — and the resolution strategy defines the table. Python's dict and set are hash tables using open addressing.

Why it matters

Because the hash table is the workhorse of practical computing — it turns countless O(n²) problems into O(n). Understanding how it hits O(1) (and how it degrades to O(n) with a bad hash or a full table) is one of the most common senior interview probes, and it's why __hash__/__eq__ from Book I matter.

How — the core of a hash map (chaining)
def _index(self, key):
    return hash(key) % self._cap        # fold hash into [0, cap)

def put(self, key, value):
    bucket = self._buckets[self._index(key)]
    for i, (k, _) in enumerate(bucket):
        if k == key: bucket[i] = (key, value); return   # update
    bucket.append((key, value)); self._size += 1
    if self._size / self._cap > 0.75:       # load factor threshold
        self._resize(self._cap * 2)          # re-hash into a bigger table
When — load factor & resizing

The load factor = entries / slots. As it rises, collisions rise and O(1) drifts toward O(n). Tables therefore resize (double and re-hash everything) once past a threshold (~0.66 for CPython's dict). Resizing is O(n) but amortized away — the price of keeping lookups constant.

⚠️
Gotcha — a bad hash destroys O(1)

If every key hashes to the same slot, a hash table degenerates into a linked list: O(n) lookups. This is the basis of hash-flooding denial-of-service attacks — why Python randomizes string hashing per process (PYTHONHASHSEED). Custom __hash__ should spread values well and stay consistent with __eq__.

🔎
Chaining vs open addressing

Chaining tolerates high load factors and simple deletes but scatters memory (pointer chasing). Open addressing keeps everything in one cache-friendly array but clusters as it fills and needs tombstones so deletes don't break probe chains. CPython's dict uses open addressing with a clever probe sequence.

Q · How does a hash table achieve O(1) lookup, and when does it fail?

It converts the key to an array index in O(1) via hashing, so it jumps straight to the slot. It degrades to O(n) when many keys collide — from a poor hash function, adversarial input, or a load factor that's too high. Resizing and a good hash keep the average constant.

Q · Chaining vs open addressing — trade-offs?

Chaining stores a list per bucket: simple, handles high load and deletes gracefully, but uses extra memory and chases pointers. Open addressing stores all entries in the array itself: cache-friendly and compact, but suffers clustering at high load and needs tombstones for deletion. Open addressing usually wins on modern hardware at moderate load factors.

5 · Trees, BSTs & Balancing

What

A tree is a hierarchy of nodes with one root and no cycles. A binary search tree (BST) orders it: every left descendant < node < every right descendant, giving O(log n) search — if balanced. A self-balancing tree (AVL, red-black) performs rotations after each insert to keep height ≈ log n.

Why it matters

Because a plain BST built from sorted data degenerates into a linked list — O(n), the very thing it was meant to beat. Balanced trees guarantee O(log n) worst case, which is why they back ordered maps (C++ std::map), database indexes (B-trees are the disk cousin), and range queries a hash table can't do.

How — a left rotation
def _rotate_left(x):
    y = x.right
    x.right = y.left     # y's left subtree becomes x's right
    y.left = x           # x sinks under y
    _update(x); _update(y)   # fix cached heights, bottom-up
    return y             # y is the new subtree root
🔎
Tree traversals

In-order (left, node, right) visits a BST in sorted order. Pre-order (node, left, right) copies/serializes a tree. Post-order (left, right, node) frees/evaluates bottom-up. Level-order (BFS with a queue) processes tier by tier. Knowing which traversal yields what is a frequent interview beat.

🧠
AVL vs red-black

Both guarantee O(log n). AVL is more rigidly balanced → faster lookups, more rotations on write. Red-black is looser → fewer rotations, better for write-heavy loads (which is why language libraries and the Linux kernel favor it). Same goal, different balance/rebalance trade-off.

Q · Why not always use a hash table instead of a balanced tree?

Hash tables give O(1) point lookups but no order: you can't ask "smallest key ≥ x," iterate in sorted order, or do range queries efficiently. Balanced BSTs give O(log n) for all of those. Choose a tree when ordering/ranges matter, a hash table when you only need key→value by exact key.

Q · What makes a BST degenerate, and how is it fixed?

Inserting sorted (or reverse-sorted) keys into a naive BST creates a chain of height n — O(n) operations. Self-balancing trees fix it by rotating after inserts/deletes to keep the height within a constant factor of log n, restoring the O(log n) guarantee regardless of insertion order.

6 · Heaps & Priority Queues

What

A binary heap is a complete binary tree stored in a flat array (no pointers), maintaining the heap property: in a min-heap, every parent ≤ its children, so the minimum is always at index 0. It's the standard implementation of a priority queue.

Why it matters

Because "always give me the smallest/largest next" is everywhere: Dijkstra's shortest path, event simulation, task scheduling, top-k queries, and merging sorted streams. A heap does peek-min in O(1) and push/pop in O(log n) — far better than sorting repeatedly.

How — array arithmetic replaces pointers
# for the node at index i:
parent = (i - 1) // 2
left   = 2*i + 1
right  = 2*i + 2

def _sift_up(self, i):        # after push: bubble new leaf up
    while i > 0 and self._a[i] < self._a[(i-1)//2]:
        p = (i-1)//2
        self._a[i], self._a[p] = self._a[p], self._a[i]
        i = p                     # O(log n): one swap per level
🔎
heapify is O(n), not O(n log n)

Building a heap from an existing array by sifting down from the middle to the root is O(n) — the leaves (half the nodes) do no work, and higher nodes are few. Pushing n items one at a time would be O(n log n). This "build cheaply, then extract" is exactly how heapsort achieves O(n log n) in place.

⚠️
Gotcha — Python's heapq is a min-heap only

There's no max-heap flag. For a max-heap, push negated values (heapq.heappush(h, -x)) or wrap items in a reverse-comparing key. And a heap is not sorted — it only guarantees the root is the extreme; iterating the array is not ordered.

Q · Heap vs sorted list for a priority queue?

A heap gives O(1) peek and O(log n) insert/extract with no full ordering maintained. A sorted list gives O(1) peek and O(1) extract but O(n) insert (shifting). For a workload of interleaved inserts and extract-min (like Dijkstra), the heap's O(log n) insert wins decisively.

Q · How would you find the k largest elements in a stream?

Keep a min-heap of size k: push each item, and if the heap exceeds k, pop the smallest. What remains are the k largest, in O(n log k) time and O(k) space — far better than sorting all n items when k ≪ n.

7 · Tries (Prefix Trees)

What

A trie stores strings by sharing prefixes: each node is a character, a root-to-node path spells a prefix, and a flag marks the end of a real word. Insert, search, and prefix-check are all O(L) where L is the key length — independent of how many words are stored.

Why it matters

Because it answers questions a hash set fundamentally can't: "which words start with pre?" A hash set knows only exact membership. Tries power autocomplete, spell-checkers, IP routing tables (longest-prefix match), and T9 text entry.

How
def insert(self, word):
    node = self._root
    for ch in word:
        node = node.children.setdefault(ch, _TrieNode())   # walk/extend
    node.is_word = True       # mark the end of a real word

def autocomplete(self, prefix):
    node = self._find(prefix)     # O(L) to reach the prefix
    return [] if node is None else self._collect(node, prefix)   # DFS the subtree
🔎
Trie vs hash set

A hash set: O(L) exact lookup, no prefix support, compact. A trie: O(L) exact and prefix lookup, plus sorted iteration for free, at the cost of more memory (a node per character). Use a trie precisely when prefix operations are the point.

Q · When would you use a trie over a hash map?

When you need prefix operations — autocomplete, "all keys starting with X," or longest-prefix matching (IP routing) — which a hash map can't do without scanning everything. The trie trades extra memory for O(L) prefix queries and naturally ordered traversal.

8 · Graphs & Traversal

What

A graph is nodes (vertices) connected by edges — the most general structure, modeling anything relational: maps, social networks, dependencies, the web. Stored as an adjacency list (dict of neighbor lists, sparse-friendly) or adjacency matrix (2-D grid, dense/fast-edge-check). You explore it with BFS or DFS.

Why it matters

Because an astonishing range of problems are graph problems in disguise: shortest routes, dependency ordering (topological sort), cycle detection, connectivity, and scheduling. Recognizing "this is a graph" and reaching for the right traversal is a core problem-solving skill.

How — BFS (shortest path, unweighted)
from collections import deque
def bfs(graph, start):
    seen, q = {start}, deque([start])
    while q:
        node = q.popleft()          # FIFO → nearest-first
        for nbr in graph[node]:
            if nbr not in seen:
                seen.add(nbr); q.append(nbr)   # mark on enqueue, not dequeue
⚠️
Gotcha — mark visited on enqueue, not dequeue

In BFS, add a node to seen the moment you push it. Marking only when you pop lets the same node be enqueued multiple times before it's processed — inflating the queue and, in dense graphs, causing exponential blowup. Also: BFS's shortest-path guarantee holds only for unweighted graphs — weighted graphs need Dijkstra.

🔎
Dijkstra & union-find

Dijkstra = BFS with a priority queue: always expand the closest unfinished node, giving shortest paths on non-negative weighted graphs in O(E log V). Union-find (disjoint-set) tracks connectivity with near-O(1) union/find via path compression — the backbone of Kruskal's MST and cycle detection.

Q · BFS vs DFS — when do you pick each?

BFS (queue) explores nearest-first — use it for shortest paths in unweighted graphs and level-order problems. DFS (stack/recursion) goes deep — use it for cycle detection, topological sorting, connected components, and exhaustive path/backtracking searches. Memory differs too: BFS holds a whole frontier; DFS holds one path.

Q · Adjacency list vs adjacency matrix?

Adjacency list uses O(V+E) space and is efficient for sparse graphs and iterating neighbors — the usual choice. Adjacency matrix uses O(V²) space but gives O(1) edge-existence checks, good for dense graphs or algorithms that query arbitrary edges frequently.

9 · Sorting & Searching

What

Sorting arranges data by a key; searching finds an element. The comparison sorts that matter: mergesort (divide-and-conquer, stable, guaranteed O(n log n)), quicksort (partition around a pivot, in-place, O(n log n) average but O(n²) worst), and binary search (O(log n) on sorted data by halving).

Why it matters

Sorting is the pre-processing that unlocks binary search, deduplication, and countless greedy algorithms. And the classic sorts teach the two most important algorithmic paradigms — divide-and-conquer and the space/stability trade-off — that recur throughout the field.

How — binary search (get the invariant right)
def binary_search(a, target):
    lo, hi = 0, len(a) - 1       # INCLUSIVE bounds
    while lo <= hi:               # <= because hi is a valid index
        mid = (lo + hi) // 2
        if a[mid] == target: return mid
        if a[mid] < target: lo = mid + 1   # discard left half
        else: hi = mid - 1              # discard right half
    return -1
⚠️
Gotcha — binary search off-by-one

The endless bug: mismatching the bound convention. If hi = len(a) - 1 (inclusive), the loop is while lo <= hi and you move to mid ± 1. If hi = len(a) (exclusive), it's while lo < hi. Mixing the two causes infinite loops or missed elements. Pick one convention and hold it.

🔎
Stability matters

A stable sort preserves the relative order of equal keys — essential when sorting by multiple criteria in passes (sort by name, then stably by age). Python's sorted() (Timsort) is stable; quicksort and heapsort are not. This is a favorite interview distinction.

Q · Quicksort vs mergesort — trade-offs?

Quicksort sorts in place with O(log n) stack space and is usually fastest in practice, but has an O(n²) worst case (mitigated by randomized/median pivots) and isn't stable. Mergesort guarantees O(n log n) and is stable, but needs O(n) extra space. Choose mergesort when you need stability or worst-case guarantees, quicksort for in-place speed.

Q · Why does binary search require sorted data?

Each step discards half the search space based on comparing the target to the middle element — that decision is only valid if the data is ordered. On unsorted data the halving assumption breaks, and you must fall back to an O(n) linear scan.

10 · Recursion, Divide & Conquer, Backtracking

What

Recursion solves a problem by solving smaller instances of itself, bottoming out at a base case. Divide & conquer splits into independent subproblems, solves each, and combines (mergesort, quicksort). Backtracking explores a decision tree, abandoning ("pruning") branches that can't lead to a solution.

Why it matters

Because recursion is the natural shape of hierarchical data (trees, filesystems) and of "try all combinations" problems (permutations, N-queens, sudoku). Backtracking with good pruning turns an intractable brute force into something that finishes.

How — backtracking skeleton
def backtrack(state, choices, results):
    if is_solution(state):
        results.append(state.copy()); return       # base case
    for choice in choices:
        if not valid(state, choice): continue       # PRUNE dead branches
        state.append(choice)                     # choose
        backtrack(state, choices, results)       # explore
        state.pop()                              # un-choose (backtrack)
⚠️
Gotcha — missing/faulty base case → stack overflow

Every recursion needs a base case that's actually reached, and each call must move toward it. Miss that and you get infinite recursion — Python raises RecursionError at ~1000 frames by default. Deep-but-finite recursion (e.g., a 10,000-node linked list) can hit the same limit; convert to iteration or raise the limit deliberately.

🔎
The call stack IS a stack

Recursion uses the call stack — the same LIFO structure from §3. Any recursion can be rewritten iteratively with an explicit stack, which is how you avoid RecursionError for very deep problems and gain fine control over traversal order.

Q · What are the two essential parts of any recursion?

A base case (a stopping condition solved directly, without recursing) and a recursive case that reduces the problem toward the base case. Without a reachable base case you recurse forever; without progress toward it, likewise. Every correct recursion has both.

Q · How does backtracking differ from brute force?

Both explore the space of candidates, but backtracking prunes: it abandons a partial solution the instant it can't possibly succeed, cutting whole subtrees. Brute force enumerates everything blindly. Good pruning is what makes N-queens or sudoku solvable in reasonable time.

11 · Dynamic Programming — the Taxonomy

What

Dynamic programming (DP) solves problems with overlapping subproblems and optimal substructure by solving each subproblem once and reusing the answer. Two styles: memoization (top-down recursion + a cache) and tabulation (bottom-up, filling a table).

Why it matters

Because DP is how you turn an exponential recursion into a polynomial one — the difference between O(2ⁿ) and O(n). It's the hardest interview category precisely because it requires recognizing the two hallmarks and defining the right state. Master the taxonomy and most DP problems collapse into a handful of templates.

How — the same problem, both styles
from functools import lru_cache

@lru_cache(maxsize=None)        # TOP-DOWN memoization: cache decorates recursion
def fib_memo(n):
    return n if n < 2 else fib_memo(n-1) + fib_memo(n-2)

def fib_tab(n):               # BOTTOM-UP tabulation: fill a table iteratively
    if n < 2: return n
    a, b = 0, 1
    for _ in range(n - 1): a, b = b, a + b   # O(n) time, O(1) space
    return b

🔎
Memoization vs tabulation

Memoization (top-down) mirrors the recursion, only computes the states you actually need, and is easy to write from a brute-force solution. Tabulation (bottom-up) avoids recursion overhead/stack limits and often enables space optimization (keep only the last row/two variables, as in fib_tab). Same complexity, different ergonomics.

⚠️
Gotcha — is it actually DP?

DP requires both overlapping subproblems and optimal substructure. If subproblems don't repeat, memoization buys nothing — it's plain divide-and-conquer. If a locally optimal choice is always globally optimal, a greedy algorithm is simpler and faster. Misclassifying wastes time; identify the structure first.

Q · What two properties make a problem suitable for DP?

Overlapping subproblems (the same smaller problems recur, so caching pays off) and optimal substructure (an optimal solution is built from optimal solutions to subproblems). Without overlap it's just divide-and-conquer; without optimal substructure DP doesn't apply.

Q · How do you approach a DP problem you've never seen?

Define the state (what does dp[i] or dp[i][j] mean?), write the recurrence (how does a state depend on smaller states?), identify base cases, then choose memoization or tabulation and consider space optimization. Starting from a correct brute-force recursion and adding a cache is the reliable path.

12 · Greedy Algorithms & Bit Manipulation

What

A greedy algorithm builds a solution by always taking the locally best choice, never reconsidering. It's correct only when the problem has the greedy-choice property (a local optimum leads to a global one). Bit manipulation operates directly on binary representations for O(1)-space, branch-free tricks.

Why it matters

Greedy is the simplest, fastest paradigm when it applies — interval scheduling, Huffman coding, Dijkstra, and MST are all greedy. The hard part is proving it's correct rather than assuming it. Bit tricks show up in low-level code, hashing, flags, and subset enumeration, and they signal comfort with how data is really represented.

How — greedy interval scheduling & bit tricks
# GREEDY: max non-overlapping intervals → always pick earliest finish
intervals.sort(key=lambda iv: iv[1])    # by end time
count, end = 0, float("-inf")
for s, e in intervals:
    if s >= end: count += 1; end = e   # take it; it can't hurt

# BITS: XOR cancels pairs → the lone unpaired number, O(1) space
result = 0
for n in nums: result ^= n     # x^x==0, x^0==x

n & (n - 1)      # clears the lowest set bit (Kernighan popcount)
n & (n - 1) == 0   # n is a power of two (n > 0)
⚠️
Gotcha — greedy is often wrong

Greedy fails whenever a locally optimal choice blocks a better global one. Coin change with denominations {1, 3, 4} making 6: greedy takes 4+1+1 (three coins), but 3+3 (two coins) is optimal — that problem needs DP. Always verify the greedy-choice property (ideally with an exchange argument) before trusting it.

🔎
Subsets via bitmask

The 2ⁿ subsets of n items map to the integers 0…2ⁿ−1: bit j of the counter means "include item j." for mask in range(1<<n) enumerates every subset in one loop — a clean, allocation-free way to brute-force small combinatorial problems.

Q · When is greedy correct, and how do you know?

When the problem has the greedy-choice property (a local optimum extends to a global optimum) and optimal substructure. You prove it — typically with an exchange argument showing any optimal solution can be transformed into the greedy one without getting worse. If you can't prove it, suspect DP.

Q · How do you check if an integer is a power of two in O(1)?

n > 0 and (n & (n - 1)) == 0. A power of two has exactly one set bit; subtracting 1 flips that bit and sets all lower bits, so ANDing gives 0. It's a branch-free constant-time test with no loops or division.

🎯 Key takeaways
  • Big-O is the language of scale — know your containers' complexities cold; watch for hidden O(n) in innocent one-liners.
  • Arrays vs linked lists = random access vs cheap splicing; dynamic-array append is amortized O(1).
  • Hash tables hit O(1) via hashing; collisions (chaining vs open addressing) and load-factor resizing keep them fast.
  • Balanced trees (AVL/red-black) rotate to guarantee O(log n) and give ordering a hash table can't.
  • Heaps = O(1) peek, O(log n) push/pop, O(n) build; tries give O(L) prefix queries.
  • Graphs: BFS (queue, shortest unweighted), DFS (stack, cycles/topo), Dijkstra (PQ), union-find (connectivity).
  • DP needs overlapping subproblems + optimal substructure; greedy needs the greedy-choice property (prove it).
