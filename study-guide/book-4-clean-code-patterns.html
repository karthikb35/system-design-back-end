The Pattern Mindset
A pattern earns its place when the flexibility it provides exceeds the indirection it adds
🧠

A design pattern is a named solution to a recurring problem shape. The primary value is communication: "put a circuit breaker on that call" transmits a full design in five words. The secondary value is that the solution has been battle-tested in thousands of systems. Use both wisely.

The system used throughout

ShopFlow — a mid-size e-commerce platform: 500k daily users, product catalogue, cart, checkout, payments (Stripe), inventory, analytics, notifications. Every pattern below solves a specific, named problem that emerged as ShopFlow grew from 10k to 500k users.

✓ USE a pattern when
  • You have ≥ 2 concrete implementations
  • You need a seam for testing / injection
  • The same change is needed in N places
  • Two teams are editing the same class for different reasons
  • You can NAME the specific production problem it solves
✗ DO NOT use a pattern when
  • You have exactly one implementation (YAGNI)
  • A plain function or if/elif is clearer
  • The indirection exceeds the flexibility gained
  • You're doing it "for SOLID", not for real pain
  • Your team can't read the code without the textbook

SOLID — Five Levers for Change-Resilient Code
Each principle answers: when this requirement changes, how much code must change with it?
🧱
PrincipleThe coupling it attacksShopFlow incident / fixThe gotcha
S · SRP
Single Responsibility		A class serving multiple actors — multiple reasons to changeGodReport class changed for finance, design, and ops simultaneously → merge conflicts every sprint. Fix: split into SalesReport + HtmlFormatter + FileRepositorySRP is about ACTORS (who orders the change), not method count. A 20-method class serving one actor does NOT violate SRP.
O · OCP
Open / Closed		Adding a feature requires editing tested codecheckout() function had 150-line if/elif for pricing rules. Adding Black Friday pricing = editing the most critical function. Fix: Strategy pattern — new rule = new class, zero edits to checkout()OCP doesn't mean "never touch old code." Fixing a bug is fine. OCP is about EXTENSION — new behaviour via new code, not editing existing.
L · LSP
Liskov Substitution		Subtypes that surprise callers — the classic Square(Rectangle) violationBadSquare overrides Rectangle's independent width/height setters. Code that resizes a rectangle gets wrong area from BadSquare. Fix: Square and Rectangle as siblings under Shape, not a hierarchyisinstance() checks in business logic = LSP violation smell. If callers need to know the subtype, the contract is broken.
I · ISP
Interface Segregation		Fat interfaces force implementers to stub unused methodsFatWorker ABC forced RobotWorker to implement eat() → NotImplementedError at runtime. Fix: Protocol Workable + Protocol Eatable — Robot implements only what it doesISP violation → forced stubs → those stubs are LSP violations. The chain: fat interface ⇒ NotImplementedError stubs ⇒ caller crashes at runtime.
D · DIP
Dependency Inversion		Policy (business logic) coupled to detail (DB, HTTP, payment API)OrderService constructed MySqlDatabase inside itself — impossible to test without a real DB. Fix: inject a StoragePort abstraction; tests inject FakeStorage"new is glue." If a class constructs its own collaborators it's glued forever. DI = mechanism; DIP = the principle that the abstraction is injected, not a concrete class.
💡
DIP is the load-bearing principle

The others guide how to structure code; DIP determines testability and swappability. Once OrderService depends on StoragePort (not MySqlDatabase), you can: (1) inject a FakeStorage in tests with zero network/DB, (2) swap Postgres for Redis by changing ONE line at the composition root, (3) run tests in parallel without shared DB state. This is why FastAPI's Depends() exists — DIP as a framework feature.

Strategy — Pricing Engine
OCP + DIP crystallised into a named pattern — the most useful pattern in backend Python
♟️
🏪 ShopFlow Production Problem

Q3 planning: Marketing wants Black Friday (30% off), VIP subscribers (20% off + free shipping), B2B bulk tiers (5%/10%/15% by quantity), and flash sales (50% for 2 hours) — all live simultaneously on different user segments. These rules change every sprint. Marketing and Finance both touch the checkout function in the same sprint.

✗ Without Strategy — what broke

The checkout function grows to a 200-line if/elif. Every new pricing rule requires editing the most critical, most-tested code path in the entire system. Merge conflicts happen every sprint between the Finance team and Marketing team in the same function. Unit-testing Black Friday pricing requires setting up the entire checkout state (is_flash=False, user_type=...). A/B testing two pricing models simultaneously is architecturally impossible.

# ✗ ANTI-PATTERN — grows forever, breaks constantly
def checkout(cart_total, user_type, quantity, is_flash, is_black_friday, is_ultra_vip):
    if is_flash:             return cart_total * 0.50
    elif is_black_friday:    return cart_total * 0.70
    elif user_type == "vip": return cart_total * 0.80
    elif user_type == "b2b" and quantity > 100: return cart_total * 0.85
    # Adding ultra_vip: edit here. A/B test: add a flag. Audit: edit here again.
    else: return cart_total
✓ With Strategy — what it buys

Each rule is a class. Checkout receives the rule at call time and knows nothing about which one it is. Adding Ultra-VIP = one new class, zero edits to checkout(). A/B testing = inject different strategies per user segment. Unit-testing Black Friday = instantiate BlackFridayPricing alone, call apply().

class PricingStrategy(Protocol):
    def apply(self, ctx: CartContext) -> float: ...

class BlackFridayPricing:
    def apply(self, ctx): return ctx.total * 0.70

class TieredB2BPricing:
    def apply(self, ctx):
        if ctx.quantity < 50:  return ctx.total * 0.95
        if ctx.quantity < 100: return ctx.total * 0.90
        return ctx.total * 0.85

def checkout(cart: CartContext, strategy: PricingStrategy) -> float:
    return strategy.apply(cart)   # zero knowledge of which rule

# A/B testing: assign strategy from experiment config
strategy = experiment.assign(user_id) or StandardPricing()
checkout(cart, strategy)
🌍 Where Strategy is used in real frameworks
  • Django REST Framework: authentication backends (BasicAuthentication, TokenAuthentication, JWTAuthentication) — selected via DEFAULT_AUTHENTICATION_CLASSES
  • SQLAlchemy: connection pool strategies (NullPool, QueuePool, StaticPool) — injected into create_engine()
  • FastAPI: security schemes (OAuth2PasswordBearer, APIKeyHeader) as interchangeable strategies
  • Celery: task routing strategies (round-robin, priority, consistent hashing)

Factory Method
Decouple object creation from use — the key to swappable infrastructure
🏭
🏪 ShopFlow Production Problem

Product images: AWS S3 today, EU data-residency law forces GCP for European users, CI/CD runs against local filesystem (no cloud credentials in GitHub Actions), enterprise customers get Azure Blob. ShopFlow has ProductImageService — it must work in all four environments without conditional imports or if/elif chains.

✗ Without Factory

ProductImageService imports boto3, google-cloud-storage, AND azure-storage-blob. It crashes on import if any SDK isn't installed. Testing requires mock AWS credentials. Adding Azure = editing the core service. The imports alone couple the service to all three cloud vendors.

✓ With Factory

ProductImageService depends only on a StorageBackend Protocol. A factory function reads config once at startup and returns the right backend. Tests inject FakeBackend — no cloud credentials needed. Adding Azure = one new class + one dict entry.

class StorageBackend(Protocol):
    def upload(self, data: bytes, key: str) -> str: ...

def make_storage(config: dict) -> StorageBackend:
    return {"s3": S3Backend, "gcs": GCSBackend, "local": LocalBackend}[
        config["STORAGE_BACKEND"]]()   # created once at startup

class ProductImageService:
    def __init__(self, storage: StorageBackend): self._s = storage  # injected
    def upload(self, pid, data): return self._s.upload(data, f"products/{pid}.jpg")

# Test: no cloud credentials needed
svc = ProductImageService(FakeBackend())
url = svc.upload("prod_001", b"image data")   # fully testable
🌍 Where Factory is used in real frameworks
  • SQLAlchemy: create_engine("postgresql://...") — factory picks psycopg2 or asyncpg dialect from the connection URL
  • Django: DATABASES setting drives a connection factory — swap PostgreSQL for SQLite in tests with one line
  • FastAPI: Depends(get_db) is a factory that creates/reuses a DB session per request
  • boto3: boto3.client("s3"), boto3.client("sqs") — service factories with a uniform interface

Observer / Event Bus
Decouple "it happened" from "who reacts" — the foundation of event-driven architecture
📡
🏪 ShopFlow Production Problem

When an order is placed: send email, deduct inventory, log analytics, notify warehouse, run fraud check, award loyalty points, update dashboard. This list grows by 1–2 items every quarter. The fraud check is slow. Analytics going down means customers can't place orders — a direct call failure in a non-critical service kills the critical path.

✗ Without Observer — OrderService with 7 tight couplings

OrderService.place_order() directly calls all 7 systems synchronously. If analytics is down, checkout fails. If fraud check is slow, checkout is slow. Adding Slack notification = editing OrderService. The service changes for 7 different, unrelated reasons.

✓ With Observer — emit one event, handlers are independent

OrderService emits "order.placed" and stops. Each handler subscribes independently. One bad handler is caught and logged; others still run. Adding Slack = one new function + one subscribe() call. Zero edits to OrderService. Slow handlers can be promoted to Celery tasks independently.

class OrderService:
    def __init__(self, db, bus: EventBus): self._db, self._bus = db, bus
    def place_order(self, order):
        self._db.save(order)             # critical path
        self._bus.publish("order.placed", order.to_dict())  # ONE emission

# Independent handlers — one failing does NOT block others
bus.subscribe("order.placed", send_confirmation_email)
bus.subscribe("order.placed", deduct_inventory)
bus.subscribe("order.placed", track_analytics)   # if down: logged, not fatal
bus.subscribe("order.placed", notify_slack)       # added with ONE line, zero edits
🌍 Where Observer is used in production
  • Django Signals: post_save, pre_delete — model-level domain events for audit logging, cache invalidation
  • SQLAlchemy Events: after_insert, before_commit — ORM lifecycle hooks
  • Stripe Webhooks: Stripe publishes events; your endpoint subscribes — distributed Observer over HTTP
  • Kafka / RabbitMQ: same pattern at service-to-service scale — the message broker replaces the in-process EventBus
⚠️
Critical gotcha — memory leaks and re-entrant updates

Strong references from the event bus to handlers keep them alive forever — use weakref.ref(handler). Re-entrant update: an observer that modifies the subject during notification triggers recursive notifications. Guard with an "is_publishing" flag or use deferred delivery via a queue.

Adapter — SDK Migration
Wrap incompatible third-party interfaces — migrate without touching 47 call sites
🔌
🏪 ShopFlow Production Problem

ShopFlow migrates from Braintree to Stripe (better rates). 47 files call braintree.Transaction.sale(). Stripe has a completely different API signature. Requirements: (a) no breakage during migration, (b) A/B test 5% Stripe vs 95% Braintree, (c) rollback in under 5 minutes if Stripe is buggy.

✓ With Adapter

Define a PaymentGateway Protocol. Wrap Braintree and Stripe behind it. Migration = swap one line at the composition root. A/B routing via a SplitGateway. All 47 call sites are completely untouched.

class PaymentGateway(Protocol):
    def charge(self, amount_cents: int, token: str, user_id: str) -> str: ...

class BraintreeAdapter:
    def charge(self, amount_cents, token, user_id) -> str:
        result = self._sdk.sale(amount_cents, token, user_id)   # Braintree API
        if not result["success"]: raise RuntimeError("payment failed")
        return result["transaction_id"]

class StripeAdapter:
    def charge(self, amount_cents, token, user_id) -> str:
        result = self._sdk.create_payment_intent(            # different API
            amount=amount_cents, currency="usd", customer=user_id, payment_method=token)
        return result["id"]

# Gradual rollout: 5% Stripe, 95% Braintree
class SplitGateway:
    def charge(self, amount_cents, token, user_id) -> str:
        gw = self.stripe if random.random() < self.stripe_pct else self.braintree
        return gw.charge(amount_cents, token, user_id)

# Composition root — ONE line to migrate:
gateway = StripeAdapter(StripeSDK())   # all 47 sites unchanged ✓

Circuit Breaker
The pattern GoF forgot — the most critical pattern in distributed systems
⚡
🏪 ShopFlow Production Incident — Stripe Outage

11:47 AM: Stripe outage. Every checkout call times out after 30 seconds. ShopFlow processes 200 checkouts/minute. 11:50 AM: Thread pool (50 threads) is full of checkout requests each waiting 30s. Product catalogue requests (zero Stripe calls) can't get a thread either. Total site outage in 3 minutes from a payment service failure.

✗ Without Circuit Breaker — cascade failure
  • 200 req/min × 30s timeout = 100 threads occupied simultaneously
  • New requests (catalogue, search) queue behind the blocked threads
  • Users see "site down" from a payment service outage unrelated to the page they're on
  • When Stripe recovers, all backed-up retries hit it simultaneously (thundering herd)
✓ With Circuit Breaker — fail fast, protect the pool

After 3 failures, the breaker opens. Checkout requests fail in <1ms with "payment temporarily unavailable." Threads stay free. Catalogue/search work normally throughout the outage. After 5s, one probe is sent. On success, normal traffic resumes automatically.

🚨
Circuit Breaker ≠ Retry — use BOTH together

Retry handles transient failures (network blip, gone in <1s). Circuit Breaker handles sustained outages. Without Retry: a single bad request fails permanently. Without Circuit Breaker: retries during an outage exhaust threads and amplify load on the recovering service. The production pattern: Retry for individual calls, Circuit Breaker to stop retrying when the service is clearly broken.

🚨
The mid-level failure mode — pattern euphoria

After learning patterns, engineers reach for FactoryFactory and five interfaces to create one object. Symptom: six files to trace one function call. Every abstraction has a real cost — indirection, extra files, cognitive load. A pattern earns its place when the flexibility it provides exceeds the indirection it adds. If you can't name a concrete, existing need, don't create the abstraction.

Architect Interview Bank
30 questions — junior → senior → staff level
🏆
Q1 · What is the GoF Decorator pattern and how does it differ from Python's @decorator syntax? Junior

The GoF Decorator pattern wraps an object implementing the same interface, adding behaviour at the object level (e.g., LoggingMiddleware(AuthMiddleware(handler))). Python's @decorator syntax wraps a function. Both "add behaviour by wrapping" but target different things — one wraps objects, one wraps functions. FastAPI's @app.get() is a function decorator; Depends() uses the Factory pattern. They coexist in the same framework.

Q2 · When would you choose Strategy over a simple if/elif? Junior

When you have ≥ 2 algorithms that change independently of callers, need to be unit-tested in isolation, or configured at runtime (A/B testing, feature flags). A two-branch if that hasn't grown in 6 months doesn't need Strategy — the if-chain is clearer and has no indirection cost. The signal to refactor: two teams editing the same if-chain for different reasons in the same sprint.

Q3 · ShopFlow processes checkouts calling Stripe. Stripe has a 5-minute outage. Walk through what happens and what you'd build. Senior

Without protection: every checkout waits 30s for Stripe timeout → thread pool exhausted → ALL endpoints down (cascade failure). Fix: Circuit Breaker — after 3 failures, reject checkout in <1ms ("payment temporarily unavailable"). Threads stay free; catalogue/search remain up. After reset_timeout, one probe. On success, close. Additionally: expose HTTP 503 on checkout (not 500) so load balancer can route, and publish "checkout unavailable" event for on-call. Pair with Retry + jitter for transient blips.

Q4 · What is the difference between DI (Dependency Injection) and DIP (Dependency Inversion Principle)? Senior

DI = the mechanism: passing collaborators from outside rather than constructing them internally. You can inject a concrete class — that's DI but NOT DIP. DIP = the principle: the dependency points at an abstraction (Protocol/ABC), not a concretion. DIP flips the arrow: the detail (MySqlDatabase) implements the port that the high-level policy (OrderService) owns. FastAPI's Depends() does both: injects collaborators AND uses abstractions (Protocols) for the type hints.

Q5 · How do Strategy, Factory, and Observer compose together in a checkout service? Staff

Factory creates the Strategy: a PricingStrategyFactory reads the user's segment and returns the right PricingStrategy. Strategy is passed to checkout, which calls strategy.apply(cart). Once checkout succeeds, the service emits "order.placed" via Observer, triggering email/inventory/analytics independently. Factory = creation, Strategy = algorithm selection, Observer = post-action fan-out. This is the complete checkout architecture for a senior engineer at ShopFlow.

Q6 · When would you NOT apply SOLID? Staff

When there's one implementation and no test seam needed (YAGNI — adding the abstraction is speculative generality). When the indirection exceeds the flexibility: a UserRepository(ABC) with one subclass forever adds complexity with no benefit. When the team is small and the code is a script, not a long-lived system. The senior signal: "I'd introduce this abstraction when the second implementation arrives, or when I need a seam for testing — not before." Patterns and principles have a cost; only pay it when you can name the payoff.

⚡ Before applying any pattern — answer these
  • Can I name the SECOND implementation this abstraction will have? No → YAGNI
  • Is the if/elif growing by one case per sprint? → Strategy
  • Does adding a new reaction require editing a core class? → Observer
  • Does the unit test need real cloud credentials? → Factory + DI
  • Does one downstream service going down cascade to the whole system? → Circuit Breaker
  • Are two teams editing the same class simultaneously for different reasons? → SRP split first
  • Can I name the production failure this pattern prevents? → Ship it. Can't → don't.
