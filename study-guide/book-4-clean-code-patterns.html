Clean Code, SOLID & Design Patterns
The craft of writing code that other people — and future you — can change
🎨

Code is read far more often than it's written, and it's changed more often than it's read. This book is about that: the habits (clean code), the principles (SOLID), and the named solutions (design patterns) that keep a codebase soft enough to change without fear. The goal is never "use more patterns" — it's low coupling and high cohesion, so that a new requirement touches one place instead of ten. Part A is the principles; Part B is the full Gang-of-Four catalog, each pattern with a runnable example.

Chapters 1–6 are the timeless principles: clean-code habits and the five SOLID levers. 1 · Clean Code Foundations

What

Clean code is code optimized for the reader: intention-revealing names, small functions that do one thing, minimal surprise, and no duplication. The guiding trio: DRY (don't repeat yourself), KISS (keep it simple), and YAGNI (you aren't gonna need it).

Why it matters

Because the bottleneck in software isn't typing — it's understanding. Clean code is the difference between a bug fix taking ten minutes or a day. It's also the substrate SOLID and patterns build on: you can't meaningfully apply the Open/Closed Principle to a 300-line function nobody can read.

How — names & small functions
# ❌ unclear: what is d? what unit? what does this return?
def calc(d, r): return d * r * 0.01

# ✅ intention-revealing names read like a sentence
def interest_for(principal, annual_rate_pct):
    return principal * annual_rate_pct * 0.01

# ✅ a function does ONE thing at ONE level of abstraction
def checkout(cart):
    total = subtotal(cart)          # each step is a named idea,
    total = apply_discounts(total)  # not a wall of inline logic
    charge(total)
PrincipleSaysFailure mode it prevents
DRYEach piece of knowledge lives in exactly one placefix-in-five-places bugs
KISSPrefer the simplest thing that worksclever code nobody can maintain
YAGNIDon't build for imagined future needsspeculative generality / dead abstraction
⚠️
Gotcha — comments that lie, and premature DRY

A comment explaining what code does duplicates the code and rots when the code changes — prefer a better name; reserve comments for why. And DRY can be over-applied: forcing two things that merely look alike into one abstraction couples unrelated code (the "wrong abstraction" is costlier than a little duplication). Rule of three — abstract on the third repetition, not the first.

🔎
Code smells — the early-warning signs

Long functions, long parameter lists, deep nesting, feature envy (a method that uses another object's data more than its own), and shotgun surgery (one change edits many files). Smells aren't bugs — they're signals that a principle is being violated and a refactor (or pattern) is due.

Q · When should you write a comment?

When the code can't express why — a non-obvious trade-off, a workaround for an external bug, a business rule, or a warning. Comments that restate what the code does are noise; improve the name or structure instead. The best comment is often the one you deleted by making the code self-explanatory.

Q · Isn't DRY always good?

No. DRY is about single-sourcing knowledge, not deleting every duplicate line. Two functions that coincidentally share code but change for different reasons should stay separate — merging them creates coupling that hurts when one needs to change and the other doesn't. Duplication is cheaper than the wrong abstraction.

2 · S · Single Responsibility Principle

What

A class should have one reason to change — it should be responsible to one actor. If a class computes a value, formats it for the UI, and saves it to disk, it answers to three different stakeholders and changes for three reasons.

Why it matters

Because responsibilities that change together should live together, and responsibilities that change for different reasons should be separated. Mixing them means a formatting tweak risks breaking persistence, and every class becomes a merge-conflict magnet. SRP is really about cohesion.

How — split the axes of change
# ✅ three classes, three reasons to change (see solid_principles.py)
class SalesReport:          # changes if the CALCULATION changes
    def total(self): return sum(self.sales)

class HtmlReportFormatter:  # changes if the PRESENTATION changes
    def render(self, report): return f"<h1>{report.total()}</h1>"

class ReportRepository:      # changes if STORAGE changes
    def save(self, name, content): ...
⚠️
Gotcha — SRP is not "one method per class"

SRP is about reasons to change, not method count. A class with ten methods that all serve one responsibility is fine; a class with two methods serving two different actors violates SRP. Ask "who requests changes to this?" — if the answer names two different roles, split it.

Q · How do you decide where to draw the SRP line?

Identify the actors (users/stakeholders) who would request a change. Group code by the actor it serves so that a single actor's change touches a single class. If the marketing team's formatting change and the DBA's schema change both edit the same class, those responsibilities belong apart.

3 · O · Open/Closed Principle

What

Software entities should be open for extension but closed for modification: you add new behavior by adding new code (a new class), not by editing existing, tested code. Polymorphism replaces the growing if/elif ladder.

Why it matters

Because editing tested code to add a case risks breaking the cases that already work — and every new requirement re-opens the same file. OCP localizes change: a new payment provider, shape, or export format is a new file the rest of the system never notices.

How — a new class, not a new branch
# ❌ every new shape edits (and re-tests) this function
def area(shape):
    if shape.kind == "circle": ...
    elif shape.kind == "square": ...   # ← ladder keeps growing

# ✅ closed for modification; open for extension
class Triangle(Shape):        # added WITHOUT touching total_area()
    def area(self): return 0.5 * self.b * self.h

def total_area(shapes): return sum(s.area() for s in shapes)
🔎
OCP is the engine behind most patterns

Strategy, Factory, Decorator, State — almost every GoF pattern exists to make some axis of change satisfy OCP. When you feel an if/elif ladder growing on the same dimension, that's the signal to introduce polymorphism (and often a pattern).

Q · Doesn't OCP mean I can never edit a class?

No — it means the common, anticipated axis of change should be extendable without modification. You still fix bugs and refactor. The art is predicting which axis will change often (payment providers, shapes, formats) and making that one open; over-applying OCP to axes that never change is speculative complexity (YAGNI).

4 · L · Liskov Substitution Principle

What

Objects of a subtype must be usable anywhere the base type is expected, without breaking correctness. A subclass may not strengthen preconditions, weaken postconditions, or violate invariants the base promised. "Is-a" must mean "behaves-as."

Why it matters

Because polymorphism only works if substitutes keep their promises. An LSP violation means a caller written against the base type breaks when handed a subtype — the abstraction leaks, and every caller needs isinstance checks, defeating the point of inheritance.

🚫
The classic trap — Square extends Rectangle

A Rectangle promises "set width and height independently." A Square that inherits it must force width == height, so setting the width silently changes the height — breaking any code that assumed independence (e.g., r.width = 4; r.height = 5; assert area == 20). Inheritance modeled the shape hierarchy but broke the behavioral contract. Fix: make them siblings, not parent/child.

How — siblings that both honor the contract
class Rectangle:
    def area(self): return self._w * self._h

class SquareLSP:              # NOT a subclass of Rectangle
    def area(self): return self._s * self._s

def area_of(shape): return shape.area()   # both substitute safely
Q · How do you detect an LSP violation?

Look for subclasses that override a method to do nothing, raise NotImplementedError, tighten what inputs they accept, or surprise callers (like Square changing height when width is set). If callers need isinstance checks or comments like "don't pass a Penguin here," the hierarchy violates LSP — prefer composition or a redesigned abstraction.

5 · I · Interface Segregation Principle

What

No client should be forced to depend on methods it doesn't use. Prefer many small, role-focused interfaces over one fat, general-purpose one. In Python, that means small Protocols / ABCs.

Why it matters

Because a fat interface couples every implementer to every method. Force a RobotWorker to implement eat() from a Worker interface and you get meaningless stubs, and a change to eat() needlessly recompiles/retests robots. Small roles keep dependencies honest.

How — split the fat interface into roles
class Workable(Protocol):
    def work(self) -> str: ...

class Eatable(Protocol):
    def eat(self) -> str: ...

class Robot:                  # implements ONLY Workable — no dead eat()
    def work(self): return "welding"

def run_shift(workers: list[Workable]): # asks for the narrowest role it needs
    return [w.work() for w in workers]
Q · How does ISP relate to the other principles?

ISP is SRP applied to interfaces: one interface, one role. It also enables DIP — clients depend on the small abstraction they actually need, so they're not dragged along by unrelated methods. Fat interfaces are a form of low cohesion at the contract level.

6 · D · Dependency Inversion Principle

What

High-level policy should not depend on low-level details — both should depend on an abstraction. And the abstraction shouldn't depend on details; details depend on the abstraction. In practice: program to an interface and inject the concrete implementation.

Why it matters

Because it's what makes code testable and swappable. If OrderService constructs a concrete MySqlDatabase inside itself, you can't test it without a real database and can't switch stores. Depend on a Gateway abstraction and inject it, and you can pass a fake in tests and Postgres in production — same service.

How — inject the abstraction
class NotificationGateway(Protocol):
    def send(self, to, msg) -> None: ...

class OrderService:
    def __init__(self, gateway: NotificationGateway):  # injected, not constructed
        self._gateway = gateway
    def place(self, customer):
        self._gateway.send(customer, "Order confirmed")  # swap email↔sms freely
🔎
DIP vs Dependency Injection

DIP is the principle ("depend on abstractions"). Dependency injection is a common technique for achieving it — passing dependencies in (via constructor, setter, or a framework's Depends) instead of creating them internally. FastAPI's Depends and Spring's IoC container are DI machinery serving DIP.

Q · Why does DIP make code more testable?

Because the concrete dependency is passed in, a test can inject a fake/stub that records calls or returns canned data — no real database, network, or clock needed. The high-level logic is exercised in isolation, fast and deterministically. Hard-coded new/constructor calls make that impossible.

7 · What Design Patterns Are

What

A design pattern is a named, reusable solution to a recurring design problem — not code to copy, but a shared vocabulary and a proven structure. The 23 classic "Gang of Four" patterns split into three families by what they organize: object creation, object composition, and object communication.

Why it matters

Because "let's use a Strategy here" conveys an entire design in two words to anyone who knows the vocabulary. Patterns capture hard-won solutions so you don't reinvent them, and they're a lingua franca in code review and interviews. But they're a means to SOLID ends — never a goal.

⚠️
Gotcha — a pattern is a solution, not a requirement

The goal is never "how many patterns can I use?" Patterns earn their complexity only when the problem they solve is actually present. Reaching for a Factory when a plain constructor works, or an Abstract Factory with one product family, adds indirection with no benefit — a smell called "pattern-happy" code.

Q · What problem do design patterns actually solve?

They give proven, named solutions to recurring design problems and a common vocabulary to discuss them. They don't add features — they organize code so it's easier to change and communicate. Their value is decoupling and shared understanding, not the patterns themselves.

8 · Creational Patterns

What

Creational patterns control how objects are created, decoupling client code from concrete classes. The five: Factory Method, Abstract Factory, Builder, Prototype, and Singleton.

PatternIntentReach for it when…
Factory MethodDefer which class to instantiate to a subclass/functionthe concrete type depends on input/config
Abstract FactoryCreate whole families of related objectsyou swap an entire stack (AWS↔GCP) at once
BuilderConstruct a complex object step-by-stepmany optional params / order-sensitive assembly
PrototypeCreate by cloning an existing instanceconstruction is expensive; copy is cheaper
SingletonGuarantee exactly one instanceshared config/registry (prefer DI instead)
How — Factory Method & Abstract Factory
# Factory Method — pick the concrete type behind one call
def make_repo(kind):
    return {"json": JsonRepo, "sql": SqlRepo}[kind]()   # client stays decoupled

# Abstract Factory — swap a whole family at once (see creational.py)
def provision(factory):        # factory = AwsFactory() or GcpFactory()
    store = factory.make_storage()      # S3 or GCS
    queue = factory.make_queue()        # SQS or PubSub — always MATCHED
    return store, queue
🚫
Singleton — the pattern to distrust

A Singleton is a global in disguise: it hides dependencies, couples everything to it, and makes tests order-dependent (shared mutable state leaks between tests). Ninety percent of the time, dependency injection of a single shared instance gives you "one instance" without the global. Reach for a true Singleton rarely and deliberately.

Q · Factory Method vs Abstract Factory?

Factory Method creates one product and defers the concrete choice (one method, often subclass-overridden). Abstract Factory creates families of related products through multiple methods, guaranteeing the pieces match (all-AWS or all-GCP, never mixed). Use Factory Method for a single varying type; Abstract Factory when a whole set must vary together.

Q · Builder vs a constructor with many arguments?

Builder shines when an object has many optional parameters or requires ordered, validated assembly — it avoids telescoping constructors and unreadable positional-arg soup, and can enforce invariants before producing the final immutable object. For a few simple params, a constructor (or dataclass) is clearer; don't add a Builder prematurely.

9 · Structural Patterns

What

Structural patterns compose objects into larger structures while keeping them flexible. The seven: Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy.

PatternIntentReach for it when…
AdapterMake an incompatible interface fit yourswrapping a third-party SDK with the "wrong" shape
BridgeSplit an abstraction from its implementationtwo dimensions vary independently (shape × renderer)
CompositeTreat individual objects & groups uniformlytree structures (files/folders, UI, org charts)
DecoratorAdd behavior by wrapping, same interfacelayering logging/caching/auth without subclass explosion
FacadeOne simple entry point over a complex subsystemhiding a messy multi-step API behind one call
FlyweightShare immutable intrinsic state across many objectsmillions of near-identical objects (glyphs, tiles)
ProxyStand in to control accesslazy loading, caching, access control, remoting
How — Adapter & Decorator
# Adapter — the SDK's method is sendText(); our code expects send()
class SmsAdapter:            # implements OUR Notifier interface
    def __init__(self, sdk): self._sdk = sdk
    def send(self, msg): self._sdk.sendText(msg)   # translate the call

# Decorator — same interface, added behavior (see structural.py)
class LoggingDecorator:
    def __init__(self, wrapped): self._wrapped = wrapped
    def handle(self, req):
        log(req); return self._wrapped.handle(req)   # delegate + augment
🔎
Adapter vs Facade vs Proxy — they all "wrap"

All three put an object in front of another, but the intent differs: Adapter changes an interface to match what you need; Facade simplifies a complex subsystem behind one friendly call; Proxy keeps the same interface but controls access (lazy load, cache, permissions). Same shape, three different reasons.

Q · Decorator vs inheritance for adding behavior?

Inheritance fixes behavior at compile time and explodes combinatorially (LoggedCachedAuthService…). Decorator composes behavior at runtime by wrapping — you stack auth + logging + cache in any order, add or remove layers dynamically, and keep each concern in its own small class. It's OCP via composition.

Q · When is a Proxy the right call?

When you need to control access to an object without changing its interface: lazy-loading an expensive resource until first use, caching results, enforcing permissions, or standing in for a remote object. The client uses it exactly like the real thing; the proxy adds the guard transparently.

10 · Behavioral Patterns

What

Behavioral patterns manage how objects communicate and share responsibility. The eleven: Strategy, Observer, Command, State, Template Method, Chain of Responsibility, Iterator, Mediator, Memento, Visitor, and Interpreter.

PatternIntentReach for it when…
StrategySwap an algorithm at runtimemultiple interchangeable ways to do one thing
ObserverNotify many dependents on state changeevent/pub-sub, UI binding, reactive updates
CommandPackage a request as an objectundo/redo, queuing, logging operations
StateChange behavior when internal state changesreplacing an if state == lifecycle ladder
Template MethodFix the skeleton, vary the stepsa fixed algorithm with pluggable stages
Chain of ResponsibilityPass a request along handlersmiddleware, escalation, validation pipelines
IteratorTraverse without exposing internalscustom collections (Python: __iter__)
MediatorCentralize many-to-many communicationcomponents that would otherwise all reference each other
MementoCapture/restore state without breaking encapsulationsnapshots, undo checkpoints
VisitorAdd operations over a fixed object structurenew operations on a stable type hierarchy (ASTs)
InterpreterEvaluate sentences in a small languagesimple DSLs, expression evaluation
How — Strategy & Observer (the two you'll use most)
# Strategy — inject the algorithm; no if/elif on "kind" (see behavioral.py)
def checkout(amount, discount_strategy):
    return amount - discount_strategy(amount)   # swap % off / flat / none freely

# Observer — subject notifies subscribers on change (pub/sub)
class Subject:
    def __init__(self): self._subs = []
    def subscribe(self, fn): self._subs.append(fn)
    def notify(self, event):
        for fn in self._subs: fn(event)   # each observer reacts independently
🔎
State & Strategy are structural twins

Both delegate to a swappable object, but the intent differs. Strategy lets the client choose an algorithm; the strategies don't know about each other. State lets the object change its own behavior as it transitions (Pending → Paid → Shipped), and states often decide the next state. Same mechanics, different driver of the change.

⚠️
Gotcha — Observer & memory leaks / ordering

Observers that never unsubscribe keep the subject holding references — a classic memory leak (use weak references for long-lived subjects). And don't rely on notification order or mutate the subscriber list during notification; iterate a copy. Pub/sub decoupling is powerful but hides the call graph, so failures are harder to trace.

Q · Strategy vs State — how do you tell them apart?

Structurally identical (delegate to a pluggable object), they differ in intent. Strategy encapsulates interchangeable algorithms chosen by the client; the object's identity doesn't change. State encapsulates lifecycle behavior that the object switches between itself as conditions change, with states often triggering transitions. "Which discount formula?" is Strategy; "what can an order do now?" is State.

Q · Which behavioral pattern replaces a big if/elif on a status field?

State — model each status as a class implementing the same interface, and let the object hold a reference to its current state that handles requests and returns the next state. It removes the ladder, localizes each status's rules, and satisfies OCP (a new status is a new class).

11 · Choosing Wisely & Anti-Patterns

What

An anti-pattern is a common "solution" that looks helpful but creates more problems than it solves. The meta-skill of this book is knowing when not to reach for a principle or pattern — because misapplied structure is as costly as no structure.

Why it matters

Because over-engineering is the most common failure mode of engineers who just learned patterns. Ten layers of abstraction for a two-line problem is worse than the two lines. Judgment — matching the solution's weight to the problem's real complexity — is what separates senior from mid-level.

Anti-patternWhat it looks likeThe fix
God objectone class/module that does everythingSRP — split by responsibility
Pattern-happya Factory/Strategy for a one-line needYAGNI — use the plain solution
Spaghettitangled control flow, no boundariesclean boundaries, small functions
Golden hammerone favorite tool for every problemmatch the tool to the problem
Premature abstractiongeneralizing before the 2nd/3rd case existsrule of three; refactor when it recurs
🧠
Patterns are power tools

A nail gun is faster than a hammer — for a roof. For hanging one picture, it's absurd and dangerous. Design patterns are the same: enormous leverage on the recurring, genuinely complex problem they target; pure overhead on the simple one. Learn them so you recognize the problem, not so you apply them everywhere.

Q · How do you avoid over-engineering with patterns?

Start with the simplest thing that works and let real, repeated pain pull you toward a pattern (rule of three). Ask "what change is this protecting against, and is that change actually likely?" If you can't name the concrete future change, you're speculating — apply YAGNI and keep it simple. Refactoring toward a pattern later is cheap when the code is clean.

Q · A pattern and a principle conflict — which wins?

The principle. Patterns exist to serve SOLID and clean-code goals (decoupling, cohesion, cheap change). If a pattern makes the code harder to change or understand in your context, you've applied it wrongly — drop it. Principles are the "why"; patterns are one "how" among several.

🎯 Key takeaways
  • Clean code optimizes for the reader — names, small functions, DRY/KISS/YAGNI; comment the why, not the what.
  • SOLID keeps change cheap: SRP (one reason to change), OCP (extend don't edit), LSP (subtypes honor contracts), ISP (small roles), DIP (depend on abstractions, inject concretions).
  • Patterns are shared vocabulary in three families — creational (make), structural (compose), behavioral (communicate).
  • Creational: Factory Method, Abstract Factory, Builder, Prototype, Singleton (distrust the last).
  • Structural: Adapter/Facade/Proxy all wrap with different intent; Decorator composes behavior without subclass explosion.
  • Behavioral: Strategy (client picks algorithm) vs State (object changes its own behavior); Observer for pub/sub; State kills the status if-ladder.
  • Judgment beats knowledge — match the solution's weight to the problem; over-engineering is the classic post-patterns trap.
