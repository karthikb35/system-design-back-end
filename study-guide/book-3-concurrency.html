Concurrency & Parallelism
Doing many things at once — correctly — when one request is never enough
🧵

A single request is easy. Real systems handle thousands at once: web servers, crawlers, data pipelines, trading engines. The moment two pieces of work overlap in time, a new class of bug appears — one that passes every test on your laptop and corrupts data in production. This book makes concurrency boring: you'll know exactly which tool to reach for, why it works, and where it bites.

1 · Concurrency vs Parallelism

What

Concurrency is dealing with many things at once — structuring a program so multiple tasks make progress during overlapping time windows. Parallelism is doing many things at the literal same instant, on multiple CPU cores. Concurrency is about structure; parallelism is about execution. You can have concurrency on a single core (tasks take turns) and you need multiple cores for true parallelism.

Why

Because the bottleneck decides the tool. If your task spends its life waiting (network calls, disk, database) — I/O-bound — you want concurrency: overlap the waiting so one core serves thousands. If your task spends its life computing (parsing, hashing, image processing) — CPU-bound — no amount of waiting-overlap helps; you need parallelism across cores. Pick wrong and you add complexity for zero speedup.

How

Python gives you three tools. Threads (threading) — concurrency with shared memory, best for I/O. Processes (multiprocessing) — parallelism with separate memory, best for CPU. Asyncio (async/await) — concurrency on a single thread via an event loop, best for massive I/O fan-out. All three are covered here.

When

Ask one question first: "Is my task waiting or computing?" Waiting → threads or asyncio. Computing → processes. If you can't answer, measure before you parallelize — most "slow" code is I/O-bound and doesn't need cores at all.

🍳
The kitchen analogy

One cook (one core) can make concurrent progress on many dishes by stirring one while another simmers — that's overlapping the waiting (I/O). But chopping ten kilos of onions is pure work: one cook can't chop faster by "interleaving." You need more cooks (more cores / processes). Threads and asyncio add stirring skill; processes add cooks.

Q · Concurrency vs parallelism in one sentence?

Concurrency is structuring a program so tasks make progress in overlapping windows (can be one core); parallelism is executing tasks at the same instant on multiple cores. Concurrency is about dealing with many things; parallelism is about doing many things.

Q · How do you decide between threads, processes, and asyncio?

By the bottleneck. I/O-bound with modest fan-out → threads. I/O-bound with huge fan-out (thousands of sockets) → asyncio. CPU-bound → processes (to bypass the GIL). When in doubt, profile: if the CPU is near idle while the program is slow, it's I/O-bound.

2 · The GIL — Python's Global Interpreter Lock

What

The GIL is a single lock inside CPython (the standard interpreter) that allows only one thread to execute Python bytecode at a time. It exists to make memory management (reference counting) simple and fast for the common single-threaded case.

Why it matters

Because it means threads do not give you CPU parallelism in CPython. Ten threads doing pure Python math run no faster than one — they take turns holding the GIL. But threads do help I/O, because blocking calls (time.sleep, socket reads, DB queries) release the GIL while they wait, letting other threads run. So the GIL punishes CPU work and is harmless for I/O work.

How to beat it

Three escapes: (1) Processes — each has its own interpreter and its own GIL, so they run truly parallel. (2) C extensions — libraries like NumPy release the GIL during heavy math. (3) Free-threaded Python — an experimental build (PEP 703, Python 3.13+) that removes the GIL; not yet the default. For interviews, know escapes 1 and 2 cold.

⚠️
Gotcha — "just add threads" for a slow loop

A common junior fix for a slow number-crunching loop is to spread it across threads. In CPython this gives zero speedup (often a slight slowdown from context-switching) because the GIL serializes the bytecode. The senior move: recognize it's CPU-bound and use a ProcessPoolExecutor, or push the math into NumPy/C.

Q · What is the GIL and why does it exist?

It's a mutex in CPython that lets only one thread run Python bytecode at a time. It exists because CPython's memory management (reference counting) isn't thread-safe without it; the GIL makes the single-threaded case fast and the interpreter simple. The cost is that threads can't parallelize CPU-bound Python.

Q · If the GIL blocks parallelism, why are Python threads useful at all?

Because I/O releases the GIL. When a thread makes a blocking call — a socket read, a DB query, time.sleep — it lets go of the GIL so other threads run. For I/O-bound workloads (most web/backend work) threads overlap the waiting and give big real-world speedups.

Q · How do you achieve true CPU parallelism in Python?

Use processes (multiprocessing / ProcessPoolExecutor) so each worker has its own interpreter and GIL; or use libraries that drop to C and release the GIL (NumPy, Cython, native extensions); or, experimentally, a free-threaded (no-GIL) Python build.

3 · Threads

What

A thread is an independent path of execution within one process, sharing that process's memory. Python exposes them via the threading module and, more conveniently, via concurrent.futures.ThreadPoolExecutor.

Why

Because shared memory makes coordination cheap and threads are lightweight to start. For I/O-bound work — call five APIs, read many files — threads let the waits overlap so total time collapses toward the slowest call instead of the sum.

How

Prefer a pool over hand-managing threads. pool.map runs a function over an iterable concurrently and returns results in order.

from concurrent.futures import ThreadPoolExecutor
import time

def fake_io(seconds):
    time.sleep(seconds)          # releases the GIL -> other threads run
    return seconds

tasks = [0.2] * 5            # 5 × 0.2s = 1.0s if done one-by-one
start = time.perf_counter()
with ThreadPoolExecutor(max_workers=5) as pool:
    results = list(pool.map(fake_io, tasks))
print(time.perf_counter() - start)   # ≈ 0.2s — the waits overlapped
When

Reach for threads when work is I/O-bound and the fan-out is modest (tens to low hundreds). For thousands of concurrent connections, asyncio scales better (a thread costs ~MBs of stack). For CPU-bound work, don't — use processes.

⚠️
Gotcha — threads share memory, so bugs are shared too

Because threads share the same variables, two threads touching the same mutable object without a lock is a race condition (Section 5). The convenience of shared memory is exactly what makes threads dangerous. Rule: share as little mutable state as possible; hand data between threads with a queue.Queue.

Q · What's the difference between pool.map and submitting Futures?

map is for a uniform function over an iterable and returns results in input order. submit returns a Future per call so you can attach callbacks, gather as they complete (as_completed), or cancel. Use map for simple fan-out, submit for heterogeneous tasks or streaming results.

Q · How many threads should a pool have?

For I/O-bound work, more than cores — sized to how many calls can be "in flight" without overwhelming the downstream (e.g. 20–100). For CPU-bound work threads don't help, so the answer is "use processes, sized to cores." Always bound the pool; unbounded threads exhaust memory and thrash.

4 · Processes

What

A process is an independent program with its own memory space and its own Python interpreter (and therefore its own GIL). Python exposes them via multiprocessing and concurrent.futures.ProcessPoolExecutor — the same API as thread pools, so switching is a one-line change.

Why

Because separate interpreters mean real parallelism: four processes crunch numbers on four cores at once, bypassing the GIL entirely. This is the only way to make CPU-bound pure-Python code faster.

How

Note the identical API — only the executor class changed:

from concurrent.futures import ProcessPoolExecutor

def count_primes(limit):
    return sum(1 for n in range(limit) if is_prime(n))

with ProcessPoolExecutor(max_workers=4) as pool:
    total = sum(pool.map(count_primes, [30_000] * 4))   # 4 cores, ~4× faster
When

Use processes for CPU-bound work: parsing, compression, image/video, cryptography, ML preprocessing. Avoid them for tiny tasks — the cost of starting a process and pickling data across the boundary can exceed the work itself.

⚠️
Gotcha — everything crossing a process boundary is pickled

Processes don't share memory, so arguments and return values are serialized (pickled) and copied. Passing a 2 GB DataFrame to each worker copies 2 GB per worker. Unpicklable objects (open sockets, lambdas, local functions) raise errors. Design for coarse tasks that take chunks of data and return small results.

🚫
Pitfall — missing the __main__ guard on Windows

On Windows (and macOS spawn), child processes re-import your module. Without an if __name__ == "__main__": guard around the code that starts the pool, each child re-runs it, spawning children recursively until the machine falls over. Always launch process pools from inside the guard.

ThreadsProcesses
Share memory (cheap coordination, risky)Isolated memory (safe, must copy/pickle)
One GIL — no CPU parallelismOne GIL each — true CPU parallelism
~KBs to start, thousands feasible~MBs to start, sized to cores

Q · When would you pick a process pool over a thread pool?

When the work is CPU-bound. Threads can't run Python bytecode in parallel because of the GIL, so CPU work needs separate interpreters — processes. The trade-off is startup cost and pickling overhead, so processes pay off only when each task does meaningful work.

Q · What are the downsides of multiprocessing?

Higher memory (each process is a full interpreter), serialization cost and limits (data is pickled across the boundary), harder debugging, and no shared mutable state (you coordinate via queues, pipes, or shared-memory primitives). It's the right tool for CPU parallelism but heavier than threads.

5 · Race Conditions & Synchronization

What

A race condition is a bug where the result depends on the unpredictable timing of overlapping operations. The classic case: counter += 1 is not atomic — it's three steps (read, add, write). Two threads can both read the same value, both add one, and both write back — losing an update.

Why it's dangerous

Because it's non-deterministic. The code passes every test on your laptop, then silently loses money/inventory/messages in production under load. You can't fix what you can't reliably reproduce — so you prevent it by design, with synchronization.

Lock (mutex) — make a critical section atomic

How

A Lock guarantees only one thread is inside the critical section at a time. Always use it with with so it's released even on exceptions.

import threading
lock = threading.Lock()
counter = 0

def increment():
    global counter
    with lock:                 # only one thread inside at a time
        counter = counter + 1   # read-add-write is now atomic

💡
The senior default: don't share state — pass messages

Every lock you add is a chance to deadlock. The most robust concurrent designs avoid shared mutable state entirely and hand data between workers through a queue.Queue (threads) or asyncio.Queue (async). The queue does the locking for you. "Do not communicate by sharing memory; share memory by communicating."

Semaphore — a bounded connection pool

import threading
pool = threading.Semaphore(3)   # at most 3 "connections" in use

def query(i):
    with pool:                  # blocks if 3 are already in use
        talk_to_db(i)             # at most 3 concurrent DB calls
When to lock vs when to queue

Lock when many threads must touch one shared structure (a cache, a counter). Queue when you can model the work as a pipeline — producers put items, consumers get them. Prefer the queue; it's harder to misuse.

⚠️
Gotcha — the lock that isn't protecting anything

A lock only helps if every access to the shared data takes the same lock. One code path that reads/writes the data without the lock reintroduces the race. Locks are a discipline, not a decoration — audit every access.

Q · What is a race condition and how do you prevent it?

A bug where correctness depends on timing of overlapping operations, typically an unsynchronized read-modify-write that loses updates. Prevent it by making the critical section atomic — a Lock — or by removing shared mutable state and passing data through a thread-safe queue.

Q · Lock vs RLock vs Semaphore?

A Lock allows one holder; a second acquire by the same thread deadlocks. An RLock is re-entrant — the owning thread can acquire it multiple times (needed when locked methods call each other). A Semaphore(n) allows up to n holders — used to bound concurrency, not to guarantee exclusivity.

Q · Is counter += 1 thread-safe in Python? The GIL protects it, right?

No. The GIL guarantees one bytecode at a time, but += compiles to several bytecodes (load, add, store) and the interpreter can switch threads between them. So the operation is not atomic and needs a lock. The GIL prevents interpreter corruption, not application-level races.

6 · Deadlock, Livelock & Starvation

What

A deadlock is when two or more threads each hold a lock the other needs and both wait forever. Livelock — threads keep changing state in response to each other but make no progress (two people stepping side to side in a hallway). Starvation — a thread never gets the resource because others keep jumping ahead.

Why deadlocks happen — the four Coffman conditions

A deadlock needs all four at once: (1) mutual exclusion — resources aren't shareable; (2) hold-and-wait — a thread holds one while waiting for another; (3) no preemption — you can't force a lock away; (4) circular wait — a cycle of "A waits on B waits on A." Break any one and deadlock is impossible.

How to fix — global lock ordering

The most practical fix breaks circular wait: define one global order for acquiring locks and have every thread acquire in that order. If everyone takes Lock 1 before Lock 2, no cycle can form.

# DEADLOCK: A takes L1→L2, B takes L2→L1
# FIX: everyone acquires in a fixed global order (by id) 
first, second = sorted((lock_a, lock_b), key=id)
with first:
    with second:
        transfer(...)              # no cycle is possible
Other tactics

Break a different condition instead: use acquire(timeout=…) and back off (breaks no-preemption); grab all needed locks at once or none (breaks hold-and-wait); or best of all, use a single lock or a queue so there's nothing to order.

⚠️
Gotcha — deadlocks hide until load

A two-lock deadlock may need a precise interleaving that only shows up under production concurrency. It won't appear in a single-threaded test. Defend at design time: minimize locks, enforce ordering, add timeouts, and prefer queues. "It worked in testing" is not evidence of freedom from deadlock.

Q · What are the four conditions for deadlock, and how do you prevent one?

Mutual exclusion, hold-and-wait, no preemption, and circular wait — all four must hold. Prevent by breaking any one: impose a global lock ordering (kills circular wait), acquire-all-or-none (kills hold-and-wait), use lock timeouts/back-off (adds preemption), or avoid multiple locks entirely.

Q · Deadlock vs livelock vs starvation?

Deadlock — everyone is blocked forever (no progress, no CPU). Livelock — everyone is active but keeps reacting to each other and still makes no progress (busy, no CPU idle). Starvation — some threads progress but one is perpetually denied the resource by unfair scheduling.

7 · Asyncio — Single-Threaded Concurrency

What

Asyncio runs thousands of tasks on one thread using an event loop and cooperative multitasking. A async def function is a coroutine; it runs until it hits await on something slow (I/O), then voluntarily yields control back to the loop, which runs another ready coroutine. When the I/O completes, the loop resumes the first one.

Why

Because a thread costs megabytes of stack, so tens of thousands of threads are impractical — but tens of thousands of coroutines are cheap. For servers juggling huge numbers of mostly-idle connections (web sockets, chat, proxies, scrapers), asyncio scales where threads can't, with no locks needed for CPU state (only one coroutine runs at a time).

How

asyncio.gather schedules many coroutines and awaits them together — the waits overlap just like a thread pool, but on one thread.

import asyncio

async def fetch(name, delay):
    await asyncio.sleep(delay)          # non-blocking wait -> loop runs others
    return name

async def main():
    results = await asyncio.gather(          # run concurrently on ONE thread
        fetch("a", 0.1), fetch("b", 0.1), fetch("c", 0.1),
    )
    return results                        # ~0.1s total, not 0.3s

asyncio.run(main())
When

Use asyncio for high-concurrency I/O: API gateways, web servers (FastAPI), scrapers, chat/websocket servers, anything with thousands of mostly-waiting connections. Do not use it for CPU-bound work — a coroutine that computes without awaiting freezes the entire loop (see the golden rule below).

🚫
The golden rule of asyncio — never block the loop

Because it's one thread, a single blocking call (time.sleep, a synchronous requests.get, a heavy CPU loop) freezes every coroutine — all your users stall together. Use await asyncio.sleep, an async HTTP client (httpx/aiohttp), and offload CPU work with loop.run_in_executor(...) to a thread or process pool.

✅
Async locks & queues exist too

Even single-threaded, you still need coordination when a critical section spans an await (control can switch there). Use asyncio.Lock for that, and asyncio.Queue for producer/consumer pipelines — same ideas as threads, async-flavored.

Q · How does asyncio achieve concurrency on a single thread?

With an event loop and cooperative multitasking. Coroutines run until they await something slow, then yield control to the loop, which runs other ready coroutines. When the awaited I/O completes, the loop resumes the coroutine. No OS thread switching, no GIL fight — just overlapping the waiting.

Q · What happens if you call a blocking function inside a coroutine?

It blocks the entire event loop — every other coroutine stalls until it returns, because they all share one thread. Fix by using async equivalents (asyncio.sleep, async HTTP/DB clients) or offloading blocking/CPU work to a thread or process pool via run_in_executor.

Q · Do you still need locks in asyncio?

Sometimes. Only one coroutine runs at a time, so simple operations are safe — but if a critical section spans an await, control can switch mid-way and another coroutine can observe half-updated state. Use asyncio.Lock for those, or an asyncio.Queue to avoid shared state.

8 · Choosing the Right Model

The whole book compresses into one decision. Memorize this table and you can defend any concurrency choice in an interview.

🎯 Key takeaways
  • Concurrency ≠ parallelism. Concurrency overlaps tasks (can be one core); parallelism runs them at once on many cores.
  • The GIL lets one thread run Python bytecode at a time — so threads help I/O (waits release it) but never CPU work.
  • Threads for waiting, processes for computing, asyncio for massive I/O fan-out.
  • Race conditions come from unsynchronized shared state; fix with a Lock — or avoid shared state with a Queue.
  • Deadlock needs all four Coffman conditions; break one — usually with a global lock ordering.
  • Asyncio's golden rule: never block the loop; offload CPU/blocking work with run_in_executor.
