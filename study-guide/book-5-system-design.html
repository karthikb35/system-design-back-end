Part A — Distributed theory · Part B — Architecture styles

Chapters 1–6 are the physics of distributed systems: you can't beat the speed of light, you can't have consistency and availability during a partition, and every cache must eventually be invalidated. Chapters 7–11 are how you organize code and services to live within those constraints. The recurring lesson: name the trade-off, then choose on purpose.

1 · Thinking About Scale

What

Scaling is meeting growing load without falling over. Two directions: vertical (a bigger machine — more CPU/RAM) and horizontal (more machines behind a load balancer). Estimating whether a design can cope is back-of-the-envelope math on requests/sec, data size, and latency.

Why it matters

Because vertical scaling hits a hard ceiling (and a single point of failure), while horizontal scaling is effectively unbounded but forces you to confront distribution — state, consistency, and partial failure. Knowing the numbers (a memory read is ~100ns; a cross-region round trip is ~150ms — a millionfold gap) is what lets you reason about a design before building it.

OperationApprox. latencyRelative
L1 cache reference~1 ns1×
Main memory reference~100 ns100×
SSD random read~16 µs16,000×
Same-datacenter round trip~0.5 ms500,000×
Cross-continent round trip~150 ms150,000,000×
🔎
Latency, throughput, and the tail

Latency is time per request; throughput is requests per second — you can improve one at the other's expense. And averages lie: what users feel is the tail (p99/p99.9). One slow dependency in a request that fans out to 100 services almost guarantees a slow p99. Design for the tail, measure percentiles, not means.

Q · Vertical vs horizontal scaling — trade-offs?

Vertical (bigger machine) is simple and needs no code changes, but has a hard ceiling, gets expensive fast, and leaves a single point of failure. Horizontal (more machines) scales nearly without limit and adds redundancy, but forces you to handle distribution: load balancing, shared/partitioned state, consistency, and partial failure. Most large systems scale out and keep individual nodes modest.

Q · Why measure p99 latency instead of the average?

Because averages hide the users having a bad time. If 1% of requests take 2 seconds, the mean may look fine while 1 in 100 users suffers — and in fan-out systems that tail compounds. p99/p99.9 capture the worst common experience, which is what SLAs and user satisfaction actually track.

2 · CAP & Consistency Models

What

The CAP theorem says a distributed data store can guarantee at most two of: Consistency (every read sees the latest write), Availability (every request gets a non-error response), and Partition tolerance (it keeps working despite dropped messages between nodes). Since network partitions will happen, the real choice during a partition is C vs A.

Why it matters

Because it's the fork in every distributed-data decision. A bank ledger picks consistency (refuse the write rather than double-spend); a shopping cart or social feed picks availability (serve slightly stale data rather than an error). Getting this backwards — an unavailable cart or an inconsistent ledger — is a business failure, not just a technical one.

🔎
Consistency is a spectrum, not a switch

Strong: reads always see the latest write (costly coordination). Eventual: replicas converge given no new writes (fast, cheap, temporarily stale). Causal: operations that depend on each other are seen in order. Quorum systems tune it with R + W > N (read and write replica counts) to trade latency for freshness.

⚠️
Gotcha — "eventually consistent" surprises users

Under eventual consistency, a user can write a comment and not see it on refresh (their read hit a lagging replica) — the "read-your-own-writes" violation. Fixes include sticky routing to the leader for a user's own recent writes, or session/causal consistency. Don't hand-wave "eventual"; specify which guarantees each read path needs.

Q · Explain the CAP theorem in one breath.

In a distributed store, when the network partitions you can keep either consistency (reject or block to avoid stale reads) or availability (answer with possibly-stale data), not both — partition tolerance is non-negotiable because networks fail. So the design choice is CP vs AP, made per data type based on whether staleness or downtime is worse.

Q · Strong vs eventual consistency — when each?

Strong when correctness depends on the latest value: balances, inventory decrements, unique-username checks. Eventual when availability and latency matter more than instant freshness and brief staleness is harmless: social feeds, view counts, product catalogs, DNS. Many systems mix both, choosing per operation.

3 · Load Balancing & Consistent Hashing

What

A load balancer distributes requests across identical servers by a strategy (round-robin, weighted, least-connections, key-hash). Consistent hashing solves a harder version: mapping keys to servers so that adding/removing a server relocates only ~1/N of keys instead of nearly all.

Why it matters

Because the naive hash(key) % N is a trap: change N by one and almost every key remaps, so every cache misses and every shard reshuffles simultaneously — a self-inflicted outage during the very scaling event you wanted to be smooth. Consistent hashing is the backbone of distributed caches (Memcached), databases (Cassandra/DynamoDB), and shard routers.

How — the ring lookup
def get(self, key):
    h = _hash(key)
    idx = bisect.bisect(self._sorted, h) % len(self._sorted)  # first node clockwise
    return self._ring[self._sorted[idx]]
# removing a node deletes only its points → only its arc's keys move (~1/N)
Q · Why not just use hash(key) % N to shard?

Because when N changes (a server added or removed), the modulus changes for almost every key, remapping the vast majority at once — mass cache misses and shard reshuffles precisely during scaling. Consistent hashing places keys and servers on a ring so only ~1/N keys move when membership changes, making scaling incremental instead of catastrophic.

Q · What do virtual nodes solve?

With few servers, a plain ring distributes load unevenly (one server may own a large arc). Giving each physical server many virtual points spreads its ownership around the ring, evening out load and making rebalancing on add/remove smoother. It's the standard fix in real consistent-hash implementations.

4 · Caching & Content Delivery

What

A cache stores hot data close to where it's needed to cut latency and offload the backing store. Caches live at every layer: CPU, application (in-process), distributed (Redis/Memcached), and the edge (CDN). The design axes are eviction (LRU/LFU — what to drop) and write policy (cache-aside, write-through, write-back).

Why it matters

Because caching is the single highest-leverage move for read-heavy systems — turning a 50ms DB query into a 1ms lookup and shedding most load off the database. But it introduces the two hardest problems in computing: invalidation (keeping the cache in sync with the truth) and consistency (serving stale data).

Write policyHowTrade-off
Cache-asideApp reads cache; on miss, loads DB and fills cachesimple, lazy; first read is a miss
Write-throughWrite cache + DB togetherconsistent reads; slower writes
Write-backWrite cache now, flush to DB laterfast writes; data loss risk on crash
⚠️
Gotcha — cache stampede (thundering herd)

When a hot key expires, thousands of concurrent requests all miss at once and hammer the database simultaneously — often taking it down. Mitigations: a per-key lock so only one request recomputes (others wait), stale-while-revalidate (serve the old value while one refresh runs), or randomized jitter on TTLs so keys don't expire in sync.

🔎
The two hard cache problems

"There are only two hard things in computer science: cache invalidation and naming things." Invalidation is genuinely hard because the cache and the source of truth drift the instant either changes. Strategies: short TTLs (bounded staleness), event-based invalidation (publish on write), and versioned keys. Pick the weakest consistency your product can tolerate — it's the cheapest.

Q · Walk through the cache-aside pattern.

The application checks the cache first. On a hit it returns immediately. On a miss it reads the database, stores the result in the cache (with a TTL), and returns it. Writes update the database and either invalidate or update the cache entry. It's lazy (only caches what's requested) and resilient (a cache outage just means more DB load), which is why it's the most common approach.

Q · How do you prevent a cache stampede?

Ensure only one request recomputes a missing hot key: use a mutex/lock (single-flight) so concurrent misses wait for one recompute, serve stale-while-revalidate to avoid blocking, and add random jitter to TTLs so many keys don't expire simultaneously. Optionally pre-warm or asynchronously refresh very hot keys before they expire.

5 · Data Partitioning & Replication

What

Replication keeps copies of the same data on multiple nodes (for availability and read scale). Partitioning (sharding) splits different data across nodes (for write scale and capacity). Real systems combine both: shard the data, then replicate each shard.

Why it matters

Because a single database eventually can't hold the data or serve the writes. Replication removes the single point of failure and scales reads; sharding scales writes and storage past one machine. But each adds hard problems: replication lag (stale reads) and cross-shard queries/transactions (expensive or impossible).

ApproachScalesMain challenge
Leader–follower replicationreadsreplication lag; failover
Multi-leader / leaderlessreads + writes, multi-regionwrite conflicts; convergence
Range shardingwrites + storagehotspots on sequential keys
Hash shardingwrites + storageno range scans; rebalancing
⚠️
Gotcha — the hot shard & the cross-shard join

Shard by a key with skew (e.g., country, or a sequential timestamp) and one shard gets all the traffic — the others idle while it melts. Choose a high-cardinality, evenly-distributed shard key. And once sharded, a query spanning shards (a join, an aggregate) becomes a scatter-gather across the network — slow and complex. Design access patterns before choosing the shard key.

🔎
Replication lag & read-your-writes

Asynchronous replication means a follower can be milliseconds-to-seconds behind the leader. A user who just wrote and then reads from a follower may not see their change. Fixes: route a user's reads to the leader for a short window after their write, or track a version/token and read from a replica caught up to it.

Q · Replication vs partitioning — what's the difference?

Replication copies the same data to multiple nodes for availability and read scaling; partitioning (sharding) splits different data across nodes for write scaling and capacity. They're complementary: shard to spread load and storage, then replicate each shard so no single node's failure loses data. Replication fights failure; partitioning fights size.

Q · How do you choose a shard key?

Pick a key with high cardinality and even access distribution so load spreads uniformly and no shard becomes hot — and one that matches your dominant query pattern so most queries hit a single shard. Avoid sequential keys (timestamps, autoincrement IDs) that funnel writes to one shard, and avoid low-cardinality keys that create skew.

6 · Reliability Patterns

What

The techniques that keep a distributed system standing when parts fail or overload: rate limiting (cap request rate), circuit breaker (stop calling a failing dependency), idempotency (safe retries), back-pressure (slow the producer), bulkhead (isolate failures), and timeouts + retries with backoff.

Why it matters

Because in a distributed system, failure is the normal case, not the exception — dependencies time out, retries pile up, and a slow service becomes a cascading outage. These patterns turn "one component failed" into "the system degraded gracefully" instead of "everything went down together."

PatternProtects againstHow
Rate limitingoverload & abusetoken bucket / sliding window (see rate_limiting.py)
Circuit breakerhammering a dead dependencytrip open after N failures; probe to recover
Idempotency keyduplicate effects on retrydedupe by key (see 04-system-design/production_code.py)
Timeout + backoffhanging calls, retry stormsbounded waits, exponential + jitter
Bulkheadone failure sinking everythingisolate pools/threads per dependency
⚠️
Gotcha — retries without backoff cause the outage they fear

When a service slows, naive clients retry immediately and multiply the load, turning a blip into a death spiral (a "retry storm"). Always pair retries with exponential backoff + jitter, a retry budget/cap, and a circuit breaker so a struggling dependency gets room to recover instead of being pounded harder.

🔎
Idempotency makes retries safe

In an at-least-once world (networks retry), the same request can arrive twice. An idempotency key — a client-supplied unique ID stored server-side — lets the server detect the duplicate and return the original result instead of charging the card twice. It's the difference between "safe to retry" and "retries corrupt data."

Q · How does a circuit breaker work?

It wraps calls to a dependency and tracks failures. In closed state calls pass through; after too many failures it trips open and fails fast (no calls) for a cooldown, sparing both systems. After the cooldown it goes half-open, letting a probe through — success closes it, failure re-opens. This stops one slow/dead dependency from cascading into a full outage.

Q · What makes an operation idempotent, and why care in distributed systems?

Idempotent means applying it multiple times has the same effect as applying it once (e.g., "set balance to 100," or a create guarded by a unique key). It matters because networks retry: without idempotency a retried "charge $10" charges twice. Idempotency keys and naturally idempotent designs make at-least-once delivery safe.

7 · Monolith → Microservices

What

A monolith is one deployable unit containing all features. Microservices split the system into small, independently deployable services owning their own data, communicating over the network. It's a spectrum, not a binary — with the well-structured "modular monolith" in between.

Why it matters

Because the choice drives team autonomy, deployment cadence, and operational complexity. Microservices let teams ship independently and scale hot paths in isolation — but they trade in-process function calls for network calls, and local transactions for distributed ones. Choosing microservices too early is a top cause of self-inflicted complexity.

🚫
The distributed monolith — worst of both worlds

If your "microservices" must be deployed together, share a database, or chain synchronous calls for every request, you've built a distributed monolith: the operational pain of microservices with none of the independence. The cure is real boundaries — each service owns its data and can be deployed alone. Most successful microservice systems started as a monolith and split along proven seams (the "monolith first" rule).

Q · When should you choose microservices over a monolith?

When independent deployability and team autonomy are the bottleneck — many teams stepping on one release, or specific components needing separate scaling/technology. Not for a small team or early product, where the network, data-consistency, and operational costs outweigh the benefits. Start with a modular monolith and extract services along stable, high-value boundaries when the pain is real.

Q · How do services communicate, and what's the trade-off?

Synchronously (REST/gRPC request-response) or asynchronously (events/messages via a broker). Synchronous is simple and immediate but couples availability — a downstream outage propagates. Asynchronous decouples services and absorbs load spikes but adds eventual consistency and harder debugging. Many systems use sync for queries and async events for state changes.

8 · Layered, Hexagonal & Clean Architecture

What

Ways to structure a single service's internals. Layered stacks UI → business → data. Hexagonal (ports & adapters) puts the domain at the center, talking to the outside only through interfaces (ports) with pluggable implementations (adapters). Clean architecture formalizes this with the dependency rule: source-code dependencies point only inward, toward the domain.

Why it matters

Because it decides how testable and how coupled-to-infrastructure your business logic is. When the domain depends on abstractions (not on Postgres, Kafka, or FastAPI), you can test it without any of them and swap the database or framework without touching business rules. This is DIP (Book IV) applied at architectural scale.

🔎
Ports & adapters in practice

A port is an interface the domain owns (e.g., OrderRepository). An adapter implements it for a specific technology (PostgresOrderRepository, InMemoryOrderRepository for tests). The domain depends on the port; the adapter depends on the port too. Swapping Postgres for MongoDB — or a real DB for a fake in tests — changes an adapter, never the business logic. This is exactly the layered FastAPI refactor in 02-solid/production_code.py.

Q · What is the dependency rule in clean architecture?

Source-code dependencies point only inward, toward higher-level policy. Outer layers (web, database, frameworks) depend on inner layers (use cases, entities), never the reverse. The domain defines interfaces; infrastructure implements them. This keeps business rules independent of, and testable without, any external technology.

Q · How does hexagonal architecture improve testability?

Because the domain talks to the outside only through ports (interfaces), tests inject in-memory adapters instead of real databases, queues, or HTTP. The business logic runs fast and deterministically with no infrastructure, and the same domain code works unchanged against Postgres in production. Isolation of the core from I/O is the whole point.

9 · Domain-Driven Design

What

Domain-Driven Design (DDD) is an approach to complex domains that puts the business model at the center. Key ideas: a ubiquitous language shared by devs and domain experts; bounded contexts (explicit boundaries where a model and its terms are consistent); and building blocks like entities, value objects, and aggregates.

Why it matters

Because in a large system the hardest problem isn't technology — it's modeling the business correctly and drawing service boundaries that don't fight the domain. Bounded contexts are the natural seams along which to split microservices; getting them right is what makes services truly independent instead of a distributed monolith.

🔎
Aggregates & bounded contexts

An aggregate is a cluster of objects treated as one unit for consistency, with a single root that's the only entry point (e.g., an Order aggregate owning its LineItems) — you enforce invariants and transactions at the aggregate boundary. A bounded context is larger: the same word ("Customer") can mean different things in Sales vs Support, so each context has its own model. Contexts map cleanly onto service boundaries.

⚠️
Gotcha — one giant shared model

Trying to build a single canonical model of "Customer/Product/Order" for the whole company creates a bloated, over-coupled schema that no team fully owns. DDD says the opposite: let each bounded context keep its own model and translate at the edges (context mapping). Forcing one model across contexts is a classic large-system failure.

Q · What is a bounded context, and why does it matter for microservices?

A bounded context is an explicit boundary within which a domain model and its terminology are consistent and self-contained. It matters because it gives you natural, low-coupling seams to split services — each service owns one context and its data. Boundaries that follow bounded contexts stay independent; boundaries drawn arbitrarily (e.g., by technical layer) leak and re-couple.

Q · Entity vs value object?

An entity has a distinct identity that persists over time regardless of attribute changes (a User is the same user even after changing their email). A value object is defined entirely by its attributes and has no identity (a Money(100, "USD") or an Address) — two with equal values are interchangeable and usually immutable. Modeling value objects as immutable prevents a class of aliasing bugs.

10 · Event-Driven, CQRS & Event Sourcing

What

Event-driven architecture has services communicate by publishing and reacting to events ("OrderPlaced") through a broker, instead of calling each other directly. CQRS (Command Query Responsibility Segregation) splits the write model from the read model. Event sourcing stores state as an append-only log of events, rebuilding current state by replaying them.

Why it matters

Because async events decouple services in time and load: producers don't wait for consumers, spikes are absorbed by the queue, and new consumers can be added without touching producers. CQRS lets reads and writes scale and optimize independently. Event sourcing gives a perfect audit trail and time-travel — at the cost of more complexity.

⚠️
Gotcha — at-least-once delivery & distributed transactions

Message brokers typically deliver at least once, so consumers must be idempotent (processing the same event twice can't double-charge) — see idempotent_consumer.py. And you can't have a classic ACID transaction across services; use the Saga pattern — a sequence of local transactions with compensating actions to undo on failure (saga.py). Event-driven trades immediate consistency for decoupling.

🔎
CQRS + event sourcing, together and apart

They're independent but pair well. CQRS alone just separates read and write models (a denormalized read store updated from writes). Event sourcing makes the write side an event log; the read models are projections built by replaying events. Use CQRS when read/write needs diverge sharply; add event sourcing when you need a full audit trail or temporal queries — and accept the extra complexity only then.

Q · What problem does event-driven architecture solve?

It decouples services in time and load. Producers emit events without knowing or waiting for consumers, so a slow or new consumer doesn't affect the producer, and traffic spikes are buffered by the queue. This enables independent scaling and extensibility (add consumers freely), at the cost of eventual consistency and harder end-to-end tracing.

Q · What is event sourcing, and what's the catch?

Instead of storing current state, you store the ordered log of events that produced it, and derive state by replaying them. Benefits: a complete audit trail, time-travel/debugging, and easy new projections. Catches: more complexity, eventual consistency on read models, schema evolution of old events, and replay cost — so use it where auditability or temporal insight justifies the overhead.

11 · Other Styles & Choosing Wisely

What

Beyond the big ones, a catalog of styles each fit for a niche: SOA (coarse services + an ESB), serverless (functions, no server management), space-based (in-memory data grid for extreme scale), pipe-and-filter (staged processing), microkernel (plugin core), BFF (backend-for-frontend), and the strangler fig (incremental legacy migration).

Why it matters

Because there is no "best" architecture — only the best fit for your constraints: team size, scale, latency needs, and how much operational complexity you can afford. The senior skill is knowing the catalog well enough to match a style to the problem and to migrate between them safely.

StyleSweet spotWatch out for
Serverless (FaaS)spiky/event workloads, low opscold starts; vendor lock-in; long tasks
Space-basedextreme, unpredictable scalecomplexity; data-grid consistency
Pipe-and-filterdata pipelines, ETL, streamingbackpressure; stage coupling
BFFmultiple clients (web/mobile) with different needsduplication across BFFs
Strangler figmigrating a legacy monolith safelylong dual-run period; routing complexity
🧠
The strangler fig — migrate without a rewrite

Named after a vine that grows around a tree until it replaces it. You put a routing layer in front of the legacy system and, feature by feature, redirect traffic to new services — the old system shrinks until it's gone. It avoids the catastrophic "big-bang rewrite" by keeping the system running and reversible at every step. The pragmatic default for modernizing a monolith.

🎯 Key takeaways
  • Scale out, not just up — know the latency numbers and design for the p99 tail, not the average.
  • CAP forces C-vs-A during a partition; consistency is a spectrum (strong → causal → eventual) chosen per data type.
  • Consistent hashing moves ~1/N keys on scaling; hash%N reshuffles everything.
  • Caching is the top read-scale lever; the hard parts are invalidation and stampedes.
  • Replication fights failure; partitioning fights size — pick a high-cardinality shard key matching your queries.
  • Reliability patterns (circuit breaker, idempotency, backoff+jitter, bulkhead) turn failures into graceful degradation.
  • Structure matters: monolith-first, split along bounded contexts; keep the domain independent of infrastructure (hexagonal/clean).
  • Event-driven + CQRS/event-sourcing decouple and audit — at the price of eventual consistency and idempotent consumers.
  • The scalability primitives are runnable in 04-system-design/examples/ — measure them, break them, tune them.
