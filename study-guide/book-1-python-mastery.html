1 · Variables, Types & Operators

What

A variable is a name bound to an object — not a box holding a value, but a label pointing at one. You never declare a type; you assign, and the name points at whatever object you gave it. The built-in types split into immutable (can't change in place: int, float, bool, str, tuple, frozenset) and mutable (list, dict, set).

Why it matters

Because "name points at object" explains Python's most infamous bugs. Two names can point at the same mutable object (aliasing) — change it through one name and the other sees it too. And immutability is why some objects can be dict keys (they're hashable and won't change underfoot).

How
x = 42            # int (immutable)
name = "Ada"      # str (immutable)
nums = [1, 2, 3]   # list (mutable)
a, b = b, a       # tuple unpacking → swap, no temp variable
⚠️
Gotcha — == vs is

== compares values; is compares identity (same object in memory). Use == for equality and reserve is for singletons like None (if x is None). Comparing values with is works by accident for small cached ints and interned strings, then breaks for everything else — a genuinely confusing bug.

🔎
Truthiness

Empty containers ([], {}, ""), 0, and None are falsy; almost everything else is truthy. So if items: reads as "if there are items" — more Pythonic than if len(items) > 0:.

Q · Mutable vs immutable — why does it matter?

Immutable objects can't change after creation, so "editing" makes a new object; mutable ones change in place. It matters for aliasing bugs (shared references), for dict/set keys (must be immutable/hashable), and for the mutable-default-argument trap.

2 · Control Flow

What

Conditionals (if/elif/else) branch on truth; loops (for, while) repeat. Blocks are defined by indentation, not braces. Python 3.10 added match — structural pattern matching, not a plain switch.

How
for i in range(5):
    if i % 2 == 0: continue   # skip to next iteration
    if i == 3: break          # exit the loop entirely
    print(i)
else:                          # runs only if the loop finished WITHOUT break
    print("completed")

match command:                 # structural pattern matching (3.10+)
    case "start": run()
    case ["move", x, y]: move(x, y)   # destructures a list
    case _: unknown()             # wildcard / default
⚠️
Gotcha — the for…else that surprises everyone

The else on a loop runs when the loop finished without hitting break — perfect for search loops ("else: not found"). It does not mean "if the loop didn't run." Misreading this is a classic source of confusion.

Q · What does for…else do?

The else block runs only if the loop completed normally (no break). It's ideal for "search and report not-found" without a separate flag variable.

3 · The Four Collections

What

Python ships four workhorse containers. Knowing their properties and Big-O cold is the foundation of everything downstream — it's how you pick the structure that makes your hot operation cheap.

How
squares = [n*n for n in range(5)]          # list comp: [0,1,4,9,16]
prices  = {"apple": 3, "pear": 5}
prices.get("plum", 0)                    # 0 default instead of KeyError
a, b = {1,2,3}, {2,3,4}
a & b   # {2,3} intersection      a | b union      a - b difference
🔎
The collections upgrades

defaultdict (auto-creates missing values), Counter (counts in one line), deque (O(1) at both ends — your queue), namedtuple/dataclass (readable records). Reaching for these instead of hand-rolling is a mark of fluency.

Q · When would you choose a set over a list?

When you need fast membership tests or automatic de-duplication and don't care about order. x in a_set is O(1) vs O(n) for a list — turning many O(n²) algorithms into O(n).

Q · List vs tuple — why does the immutable one exist?

Tuples are immutable, so they're hashable (usable as dict keys / set members), safe to share without defensive copies, and signal "fixed record." Lists are for collections you'll grow or reorder.

4 · Functions, *args/**kwargs & Comprehensions

What

Functions package reusable behavior. Python supports positional and keyword arguments, defaults, variadic *args/**kwargs, and first-class functions — functions are objects you can pass around, store, and return.

How
def greet(name, greeting="Hi", *args, **kwargs):
    return f"{greeting}, {name}"

double = lambda x: x * 2              # anonymous one-expression function
list(map(lambda x: x*2, [1,2,3]))     # [2,4,6]
list(filter(lambda x: x>1, [1,2,3]))  # [2,3]
🚫
The mutable-default-argument trap

def add(x, items=[]): creates the list once at definition time — every call shares it, so values leak across calls. Fix: default to None and create inside: items = items or []. This is one of the most-asked Python gotchas.

Q · What are *args and **kwargs?

*args collects extra positional arguments into a tuple; **kwargs collects extra keyword arguments into a dict. They let a function accept any number of arguments and are essential for decorators and wrappers that forward arbitrary calls.

5 · Modules, Files & Exceptions

What

A module is a .py file; a package is a folder of modules. import loads them. Files are read/written with open(), always inside a with block. Runtime errors are exceptions, caught with try/except.

How
with open("data.txt") as f:   # context manager → auto-closes even on error
    for line in f:            # iterate lazily, memory-cheap
        process(line.strip())

try:
    result = risky()
except (ValueError, KeyError) as e:   # catch specific types, not bare except
    log.error(e); raise              # re-raise after logging
else:
    commit(result)                        # only if no exception
finally:
    cleanup()                             # ALWAYS runs
When — EAFP over LBYL

Python favors EAFP ("easier to ask forgiveness than permission") — try the operation and handle failure — over LBYL ("look before you leap") pre-checks. EAFP is often faster and avoids a race between the check and the use.

🚫
Never swallow with a bare except:

except: catches everything — including KeyboardInterrupt and the bugs you wanted to see — and hides the real problem. Always catch the narrowest exception you can handle, and let the rest propagate.

Q · Why with open(...) instead of open() + close()?

The with statement is a context manager: it guarantees the file closes when the block exits, even on an exception. Manual close() is easy to skip on an early return or error, leaking file handles.

6 · OOP & the Four Pillars

What

OOP bundles data (attributes) and behavior (methods) into classes; you create objects (instances) from them. Its four pillars — encapsulation, abstraction, inheritance, polymorphism — are the base ideas that SOLID and design patterns build on.

PillarMeaningOne-line example
🔒 EncapsulationBundle state with the methods that guard it; hide internalsa BankAccount hides _balance behind deposit()
🎭 AbstractionExpose what, hide how (interfaces / ABCs)you call repo.save() without knowing it's Postgres
🧬 InheritanceA subclass reuses and specializes a base classDog(Animal) reuses Animal
🔀 PolymorphismSame call, different behavior per classanimal.speak() → "Woof" or "Meow"
How
from abc import ABC, abstractmethod

class Animal(ABC):
    def __init__(self, name):   # constructor — runs on creation
        self.name = name
    @abstractmethod
    def speak(self): ...     # subclasses MUST define

class Dog(Animal):
    def speak(self): return "Woof"   # overrides — polymorphism

for a in [Dog("Rex"), Cat("Mia")]:
    print(a.speak())            # same call, different behavior
🔎
MRO — the Method Resolution Order

With multiple inheritance, Python looks methods up in a deterministic order (C3 linearization), visible as Cls.__mro__. super() follows this chain — it doesn't mean "my parent," it means "the next class in the MRO." Understanding this untangles diamond-inheritance surprises.

Q · What is self, and why is it the first parameter?

self is the instance the method was called on — Python passes it explicitly so the method can read/write that object's attributes. dog.speak() is really Dog.speak(dog).

7 · Iterators, Generators & Decorators

What

An iterator produces items one at a time via __next__; anything iterable works in a for loop. A generator is the easy way to make one — a function that yields values lazily, computing each only when asked and holding just one in memory. A decorator wraps a function to add behavior without editing it.

How
def read_big_file(path):        # process a 10GB file in constant memory
    with open(path) as f:
        for line in f:
            yield line.strip()     # produces one line at a time — lazy

total = sum(n*n for n in range(1_000_000))   # generator expr — no giant list built

import functools, time
def timed(fn):
    @functools.wraps(fn)         # preserve fn's name/docstring
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = fn(*args, **kwargs)
        print(f"{fn.__name__} took {time.perf_counter()-start:.3f}s")
        return result
    return wrapper

@timed                          # slow = timed(slow)
def slow(): time.sleep(1)
🔎
Decorators you'll meet everywhere

@property, @staticmethod/@classmethod, @functools.lru_cache (memoize — the DP trick), @dataclass, and framework routes like @app.get("/"). A decorator is just fn = deco(fn).

Q · List vs generator — when each?

A list holds all items in memory (fast repeated access, known length). A generator yields lazily (tiny memory, single pass, unknown length). Use a generator for large/infinite streams and one-time iteration; a list when you need random access or to reuse the data.

Q · How does a decorator work under the hood?

@deco above def f is exactly f = deco(f): deco receives the original function and returns a replacement (usually an inner wrapper that calls the original with *args, **kwargs and adds behavior). Use functools.wraps so the wrapper keeps the original's name/docstring.

8 · The Data Model — Advanced Dunder Methods

What

Dunder ("double underscore") methods are the hooks that let your objects plug into Python's syntax. Implement them and your class behaves like a built-in: it prints, compares, hashes, iterates, indexes, works in with, and can even be called like a function. This is Python's "protocols over inheritance" philosophy.

Why

Because it's how you build expressive, native-feeling APIs — a Money that supports + and sorting, a Playlist you can index and loop over, a Transaction that rolls back in a with block. "Pythonic" libraries are built almost entirely on the data model.

How — the equality/hash contract

The most tested dunder pair. __eq__ defines value equality; __hash__ makes an object usable as a dict key / set member. The contract: if two objects are equal, they must hash equal. Break it and your object silently misbehaves in sets/dicts.

from functools import total_ordering

@total_ordering                     # derive <=, >, >= from __eq__ + __lt__
class Money:
    def __init__(self, dollars): self.cents = round(dollars * 100)
    def __repr__(self):  return f"Money({self.cents/100:.2f})"   # dev-facing
    def __eq__(self, o): return isinstance(o, Money) and self.cents == o.cents
    def __hash__(self):  return hash(self.cents)      # equal → same hash
    def __lt__(self, o): return self.cents < o.cents
    def __add__(self, o): return Money((self.cents + o.cents)/100)

sorted([Money(3), Money(1)])      # works via __lt__
{Money(5)} & {Money(5)}            # works via __eq__/__hash__

⚠️
Gotcha — defining __eq__ without __hash__

If you define __eq__ but not __hash__, Python sets __hash__ = None and your object becomes unhashable — it can't go in a set or be a dict key. Define both together, or use @dataclass(frozen=True) which does it correctly for you.

⚠️
Gotcha — __getattr__ vs __getattribute__

__getattr__ is a fallback, called only when normal lookup fails — safe and common. __getattribute__ intercepts every access and is easy to send into infinite recursion. Reach for __getattr__ unless you truly need to intercept everything.

Q · Explain __repr__ vs __str__.

__repr__ is the unambiguous, developer-facing string (ideally eval-able), shown in the REPL and debuggers; __str__ is the readable, user-facing one used by print(). If you define only one, define __repr__ — str() falls back to it.

Q · What's the __eq__/__hash__ contract?

Equal objects must have equal hashes (the reverse isn't required). Hashes should also be stable for the object's lifetime, which is why hashable objects are typically immutable. Violating this makes objects "disappear" from sets/dicts.

9 · Descriptors, __slots__ & Metaclasses

What

Three "how classes really work" features. A descriptor is an object with __get__/__set__ that controls attribute access — the machinery behind @property, methods, and ORM fields. __slots__ replaces an instance's __dict__ with a fixed set of fields. A metaclass is a class whose instances are classes — it customizes class creation.

Why

Because they're how frameworks work. Descriptors let one Positive() validate every numeric field (DRY validation). __slots__ cuts memory and blocks attribute typos at scale. Metaclasses power auto-registration (plugins), ORMs (Django models), and ABCs. Interviewers use them to see if you understand the object model beneath the syntax.

How — a validating descriptor
class Positive:                      # reusable managed attribute
    def __set_name__(self, owner, name): self._name = "_" + name
    def __get__(self, obj, t=None):     return getattr(obj, self._name)
    def __set__(self, obj, value):
        if value <= 0: raise ValueError("must be positive")
        setattr(obj, self._name, value)

class Product:
    price = Positive()                   # one descriptor validates the field
    quantity = Positive()

# METACLASS: auto-register every subclass (the plugin pattern)
class PluginRegistry(type):
    registry = {}
    def __new__(mcs, name, bases, ns):
        cls = super().__new__(mcs, name, bases, ns)
        if bases: PluginRegistry.registry[name.lower()] = cls
        return cls
⚠️
Gotcha — __slots__ and inheritance

__slots__ saves memory and blocks typos, but a subclass that doesn't also define __slots__ quietly regains a __dict__, undoing the benefit. And slotted classes can't have arbitrary attributes set — which is the point, but surprises people who expected duck-typing flexibility.

🧠
"Classes are objects too"

In Python a class is an instance of type. A metaclass is just "the class of a class." class Foo: ... is roughly Foo = type("Foo", (), {...}). Metaclasses hook that construction — so you rarely need them, but knowing they exist demystifies ORMs and ABCs.

Q · What is a descriptor, and where is it used?

An object implementing __get__/__set__/__delete__ that controls attribute access on the owning class. It's the mechanism behind @property, bound methods, classmethod/staticmethod, and ORM/serializer fields. Use one to centralize validation or computed access across many fields.

Q · When would you actually use a metaclass?

Rarely — most needs are met by __init_subclass__, class decorators, or descriptors. Reach for a metaclass when you must customize class creation for a whole hierarchy: auto-registration, enforcing interface rules at definition time, or building a declarative API (like an ORM). "If you're not sure you need one, you don't."

Q · What does __slots__ buy you, and what's the cost?

It removes the per-instance __dict__, cutting memory (big at millions of instances) and speeding attribute access, while forbidding new attributes (catches typos). Costs: no dynamic attributes, extra care with inheritance and with features that expect __dict__ (some pickling/weakref cases).

10 · Typing, Context Managers & the Memory Model

What

Three pieces of senior polish. Type hints don't change runtime behavior but power tooling, self-document, and enable generics/Protocols. The @contextmanager decorator writes a with-block guard concisely. The memory model — reference counting plus a cyclic garbage collector — is how CPython reclaims objects.

Why

Types catch bugs before runtime and make large codebases navigable. Context managers guarantee cleanup. And understanding memory explains real production issues: why a cache leaks, why cycles need gc, and when to reach for weakref.

How — generics & Protocols (structural typing)
from typing import Generic, Protocol, TypeVar
T = TypeVar("T")

class Stack(Generic[T]):           # Stack[int] vs Stack[str] are distinct to a checker
    def push(self, item: T) -> None: ...
    def pop(self) -> T: ...

class SupportsArea(Protocol):     # structural: ANY object with .area() qualifies
    def area(self) -> float: ...

def total(shapes: list[SupportsArea]) -> float:   # Circle & Square need no shared base
    return sum(s.area() for s in shapes)
How — @contextmanager & weakref
from contextlib import contextmanager
@contextmanager
def timing(log):
    log.append("enter")
    try:
        yield                 # everything before = setup, after = teardown
    finally:
        log.append("exit")   # always runs, even on exception

import weakref
cache = weakref.WeakValueDictionary()   # entries vanish when the value is GC'd
cache["k"] = obj                       # does NOT keep obj alive → leak-free cache
When

Add type hints on public interfaces and anything non-obvious (they pay off most at scale). Use a @contextmanager for simple setup/teardown; a class with __enter__/__exit__ when it holds state. Reach for weakref for caches and back-references that must not prevent collection; call gc explicitly only in special cases (it runs automatically).

⚠️
Gotcha — type hints are not enforced at runtime

Python does not check types at runtime — def f(x: int) happily accepts a string. Hints are for you, your teammates, and static checkers (mypy/Pylance). If you need runtime validation, use explicit checks or a library like pydantic (which FastAPI uses).

Q · How does Python manage memory?

Primarily by reference counting: every object tracks how many references point at it, and it's freed the instant that count hits zero. A supplementary cyclic garbage collector periodically finds and frees reference cycles that counting alone can't. Memory pools (pymalloc) handle small-object allocation efficiently.

Q · What is a Protocol, and how is it different from an ABC?

A Protocol is structural typing — any object with the right methods satisfies it, no inheritance needed ("duck typing you can statically check"). An ABC is nominal — a class must explicitly inherit it. Protocols decouple your code from a class hierarchy; ABCs enforce an explicit contract.

Q · When would you use weakref?

When you need to reference an object without keeping it alive — caches (WeakValueDictionary), observer back-references, and breaking cycles. As soon as the last strong reference goes away, the object is collected and the weak reference reads None, so you never leak.

  • Names point at objects. Aliasing shares mutable edits; immutability enables hashing and safe sharing.
  • Know the four collections' Big-O cold — dict/set are O(1) lookup; list/tuple are ordered sequences.
  • Generators stream lazily; decorators add behavior via fn = deco(fn).
  • Dunder methods make objects native; honor the __eq__/__hash__ contract.
  • Descriptors power @property & ORMs; __slots__ saves memory; metaclasses customize class creation (rarely needed).
  • Type hints are static-only; reference counting + cyclic GC manage memory; weakref gives leak-free caches.
