1 · Variables, Names & the Object Model

What

A variable is a name bound to an object — not a box containing a value, but a label pointing at one in memory. Python never declares types; you bind a name to whatever object you assign. Every object has three properties: identity (its address in memory, returned by id()), type, and value.

Why it matters architecturally

Because "name = label on object" is the source of Python's most dangerous bugs: aliasing (two names pointing at one mutable object, so a mutation through one is visible through the other) and the mutable default argument trap. Both stem from the same fact — shared references to mutable objects. Understanding this determines whether you design safe, immutable value types or accidentally build shared-state nightmares.

How
x = 42            # int — immutable; x is a name bound to object 42
name = "Ada"      # str — immutable
nums = [1, 2, 3]  # list — mutable

a = nums           # a and nums are BOTH labels on the SAME list
a.append(4)       # mutates through 'a' → nums sees [1,2,3,4] !
assert nums == [1, 2, 3, 4]  # aliasing: shared mutation

# Safe copy patterns
safe = nums[:]     # shallow copy — new list, same inner objects
import copy
deep = copy.deepcopy(nums)  # deep copy — all new objects recursively

# == tests VALUE equality; is tests IDENTITY (same object)
list1 = [1, 2]; list2 = [1, 2]
assert list1 == list2      # equal VALUES
assert list1 is not list2  # different objects
assert None is None         # correct: use `is` for singletons only
When to apply this

Apply immutability at every boundary — function arguments, return values, cache keys, and data-transfer objects. Return copies (or use tuples/frozen dataclasses) whenever you don't want callers to be surprised by mutations. Use is only for None, True, and False — never for values.

⚠️
Gotcha — the mutable default argument trap

def f(x, acc=[]) evaluates [] once at definition time. The same list is shared on every call that doesn't pass acc. Calls accumulate state across each other — a silent, persistent bug. Always default to None and build the mutable inside the function body.

# ✕ BROKEN — shared list, accumulates across calls
def broken(x, acc=[]):
    acc.append(x); return acc   # same list every call!

# ✓ CORRECT — sentinel idiom
def fixed(x, acc=None):
    if acc is None: acc = []   # fresh list each call
    acc.append(x); return acc
Q · Python is pass-by-value or pass-by-reference?

Neither. Python is call-by-object-reference (a.k.a. call-by-sharing). The function receives a reference to the same object, but the parameter name is a new binding. Mutating in place (lst.append()) is visible to the caller; rebinding (lst = [...]) only moves the local name — the caller sees nothing. The design rule: return new values instead of mutating arguments you don't own.

2 · Truthiness & Control Flow

What

Python evaluates any object as truthy or falsy. Falsy: None, False, 0, 0.0, "", [], {}, set(). Control flow uses if/elif/else, for, while, and Python 3.10's match — structural pattern matching.

How — key patterns
# for-else: idiom for "search or default"
for n in candidates:
    if is_prime(n):
        winner = n; break
else:
    winner = None       # no break → no prime found

# match — structural pattern matching (3.10+)
match event:
    case {"type": "click", "x": x, "y": y}:  # dict pattern
        handle_click(x, y)
    case ["move", dx, dy]:                    # sequence pattern
        move(dx, dy)
    case _ if event.get("urgent"):          # guard
        escalate()
    case _:
        log_unknown(event)
🔎
Truthiness is an interface, not a special case

Any class can implement __bool__ (or __len__) to participate in truthiness — if queue: means "if the queue has items." This is the contract that makes your custom types feel native. Python calls __bool__ first; falls back to __len__ != 0; defaults to True.

3 · The Four Collections & Big-O

What

Python ships four workhorse containers — list, tuple, set, dict — plus the collections module's upgrades. Picking the right one for the hot operation is the first performance decision in every system.

🧠 Mental model — collection decision tree

Ask two questions: (1) Do I need order? If yes, mutable → list, immutable → tuple. If no, unique values → set, key-value → dict. (2) What's my hot operation? Match the O(1) column in the table above. Hashability rule: immutable types (int, str, tuple, frozenset) are always hashable → usable as dict keys and set members. Mutable types (list, dict, set) are never hashable. Comprehension forms: […] → list (eager), {…} → set/dict (eager), (…) → generator (lazy, O(1) memory). Feed generators into sum()/any()/all() when you don't need to iterate twice.

How — choosing the right collection
from collections import Counter, defaultdict, deque

# Counter — frequency map in one call
freq = Counter("mississippi")   # {"s":4, "i":4, "p":2, "m":1}
top2 = freq.most_common(2)       # [("s",4),("i",4)]

# defaultdict — no KeyError on missing keys
groups = defaultdict(list)
for item in data:
    groups[item.category].append(item)  # auto-creates the list

# deque — O(1) append/pop from BOTH ends (list popleft is O(n))
q = deque(maxlen=1000)   # bounded queue / sliding window
q.appendleft("event")      # O(1) prepend

# Comprehensions — the Pythonic loop replacement
squares = [n*n for n in range(10)]
evens   = {n for n in range(20) if n%2==0}
lookup  = {word: len(word) for word in words}
lazy    = (n*n for n in range(10**6))  # generator — O(1) memory
🔎
The set-vs-list membership trap in production

A for item in big_list: if item in another_list: inner loop is O(n²). Convert another_list to a set before the loop and the membership check becomes O(1), making the whole thing O(n). This is the most common algorithmic upgrade in code reviews.

Q · When would you use a deque instead of a list?

When you need O(1) append or pop from both ends. list.pop(0) is O(n) because it shifts every element; deque.popleft() is O(1). Use deque for queues (BFS), sliding windows (maxlen), and producer-consumer buffers. Use a list when you need O(1) random indexing.

4 · Functions, Closures & LEGB Scope

What

Functions in Python are first-class objects — they can be passed as arguments, returned from other functions, and stored in variables. Scope resolution follows LEGB: Local → Enclosing → Global → Built-in. A closure is a function that captures variables from its enclosing scope.

How — closures, *args/**kwargs, and the sentinel pattern
# Closure: inner function captures 'factor' from enclosing scope
def make_multiplier(factor):
    def multiply(x):
        return x * factor   # 'factor' lives in E-scope; captured
    return multiply

triple = make_multiplier(3)
assert triple(10) == 30       # 'factor' is still 3, stored in closure

# *args (positional) and **kwargs (keyword) — variadic signatures
def greet(name, greeting="Hi", *extras, **metadata):
    return f"{greeting}, {name} | extras={extras} | meta={metadata}"

# Mutable default — ALWAYS use None sentinel
def add_item(x, items=None):
    items = items if items is not None else []  # safe
    items.append(x); return items

# functools utilities (functional-style)
from functools import partial, reduce
double = partial(multiply, factor=2)  # 'bake in' an argument
total  = reduce(lambda a, b: a + b, [1,2,3,4], 0)  # fold
⚠️
Gotcha — the late-binding closure trap

fns = [lambda: i for i in range(3)] — all three lambdas share the same i variable from the enclosing loop. When called later, i is already 2. Fix: bind the current value with a default argument: lambda i=i: i. Same root cause as the mutable default trap — the closure captures the variable, not its value at capture time.

4a · nonlocal, global & the Walrus Operator :=

What

nonlocal lets an inner function rebind a variable in the enclosing scope — essential for closures that maintain state. global rebinds a module-level name from inside a function. The walrus operator (:=, Python 3.8+) assigns and returns a value in one expression — useful in while conditions and comprehensions to avoid computing a value twice.

# nonlocal: rebind a captured variable in the enclosing scope
def make_counter():
    count = 0
    def inc():
        nonlocal count    # without this, count += 1 raises UnboundLocalError
        count += 1; return count
    return inc

counter = make_counter()
assert counter() == 1
assert counter() == 2   # state persists in the closure

# walrus := — assign inside an expression (avoids computing twice)
import re
if (m := re.search(r"(\d+)", text)):   # assign and test in one step
    print(m.group(1))                    # m is in scope here

# walrus in while — read until empty chunk
while chunk := f.read(8192):           # assign and check truthiness
    process(chunk)

# walrus in comprehension — filter and transform in one pass
results = [v for x in data if (v := expensive(x)) is not None]
🔎
Why nonlocal raises UnboundLocalError without declaration

The key: you can mutate a captured mutable object (lst.append(x)) without nonlocal — you're calling a method through an existing reference. But count += 1 desugars to count = count + 1, which is an assignment. Python compiles any assigned name in a function as a local variable at compile time. Without nonlocal, Python reads the right-hand count as a local that hasn't been assigned yet — hence UnboundLocalError. The nonlocal declaration tells the compiler to look in the enclosing scope instead.

5 · Files, Modules & Exception Handling

What

Python uses EAFP (Easier to Ask Forgiveness than Permission) as its exception philosophy: try the operation, catch specific failures — as opposed to LBYL (Look Before You Leap), which pre-checks conditions. Exceptions are objects in a class hierarchy; context managers (with) guarantee resource cleanup even when exceptions occur.

How — EAFP + context managers + domain exceptions
# Custom domain exception — communicates a business rule failure
class PaymentDeclined(Exception):
    pass

# EAFP: try the operation, handle the specific failure
def safe_int(value: str, default: int = 0) -> int:
    try:
        return int(value)
    except ValueError:
        return default

# try / except / else / finally — all four branches
try:
    result = charge(balance=100, amount=250)
except PaymentDeclined as e:
    log.error(str(e))         # specific failure
else:
    notify_success(result)    # runs only if NO exception
finally:
    close_session()           # ALWAYS runs — cleanup

# Context managers — guaranteed teardown even on exception
with open("data.csv", encoding="utf-8") as f:
    lines = f.readlines()     # file closes on __exit__, error or not
💡
EAFP vs LBYL — why EAFP is usually right

LBYL: if key in d: return d[key] — the check and the access are two separate operations; between them another thread could delete the key (TOCTOU race condition). EAFP: try: return d[key] except KeyError: ... — atomic, expressive, and works correctly under concurrency. In Python, EAFP is idiomatic; prefer it unless the check is significantly cheaper than the operation and you're not worried about races.

5a · Exception Chaining & contextlib.ExitStack

# raise X from Y — preserves the original cause in the traceback
try:
    result = json.loads(raw)
except json.JSONDecodeError as e:
    raise ValueError(f"Invalid config at line {e.lineno}") from e
    # "During handling... ValueError" shows BOTH exceptions in traceback

# raise X from None — hides implementation detail, clean public API
try:
    return self._cache[key]
except KeyError:
    raise CacheMiss(key) from None   # caller sees CacheMiss, not KeyError internals

# ExitStack: manage N context managers dynamically
from contextlib import ExitStack
with ExitStack() as stack:
    files = [stack.enter_context(open(f)) for f in file_paths]  # all closed on exit
    process(files)
🔎
raise X from Y in production debugging

Without explicit chaining, translating a low-level exception to a domain exception loses the original stack frame — KeyError on line 47 disappears, and you're left debugging why DomainError was raised with no context. Use raise DomainError(...) from original when the cause is useful for debugging; use from None when it's an implementation detail that callers shouldn't depend on. The difference shows up immediately in Sentry or CloudWatch logs at 3 AM.

6 · OOP — Four Pillars, ABCs & MRO

What

Python OOP rests on four pillars: Encapsulation (bundling state with the methods that guard it), Abstraction (exposing a clean interface, hiding the how), Inheritance (reusing and specializing a base class), and Polymorphism (the same call, different behavior per type). Python resolves multiple inheritance using the C3 linearization algorithm to produce a deterministic Method Resolution Order (MRO).

How — OOP patterns
from abc import ABC, abstractmethod
from dataclasses import dataclass, field

# Abstraction via ABC — forces subclasses to implement the contract
class Animal(ABC):
    @abstractmethod
    def speak(self) -> str: ...    # cannot instantiate Animal directly

class Dog(Animal):
    def speak(self) -> str: return "Woof"   # polymorphism: same call, Dog result

# classmethod = alternative constructor; staticmethod = utility
class Temperature:
    @classmethod
    def from_fahrenheit(cls, f): return cls((f - 32) * 5 / 9)
    @staticmethod
    def is_freezing(c): return c <= 0

# dataclass — auto-generates __init__, __repr__, __eq__
@dataclass
class Point:
    x: float; y: float
    def __add__(self, o): return Point(self.x+o.x, self.y+o.y)

# super() follows the MRO — do NOT call Parent.method(self) directly
class LoggedDog(Dog):
    def speak(self):
        result = super().speak()   # calls Dog.speak via MRO
        return f"[logged] {result}"
🧠 Mental model — IS-A vs HAS-A vs CAN-DO

IS-A (Inheritance): use when a subclass truly IS a more specific kind of the parent (Dog(Animal), ElectricCar(Car)). The MRO decides which method to call. HAS-A (Composition): use when a class uses another (Car has an Engine). Prefer composition — it's easier to swap and test. CAN-DO (Protocol/Duck typing): use typing.Protocol when you only care that an object has certain methods — no inheritance required. The classmethod/staticmethod split: @classmethod receives the class as first arg (cls) — use for alternative constructors that respect subclassing; @staticmethod receives nothing — use for pure utilities logically belonging to the class.

⚠️
Gotcha — using Parent.method(self) breaks cooperative multiple inheritance

Calling Dog.speak(self) hard-codes the parent and skips the MRO. In a multiple-inheritance chain it can call the same ancestor twice or skip a mixin entirely. Always use super() so Python's C3 MRO routes the call correctly to the next class in line.

6a · Dataclass Advanced — frozen, slots, __post_init__

from dataclasses import dataclass, field

# frozen=True: immutable after construction, auto-generates __hash__
@dataclass(frozen=True)
class Money:
    amount: float; currency: str = "USD"
    # Money(10) == Money(10) is True; can be a dict key; thread-safe

# slots=True (3.10+): no per-instance __dict__ — ~50% smaller instances
@dataclass(slots=True)
class Coord:
    x: float; y: float   # Coord().z = 1 → AttributeError (typo protection)

# __post_init__: validation and computed fields AFTER __init__
@dataclass
class Order:
    items: list[str]
    discount: float = 0.0
    def __post_init__(self):
        if not (0 <= self.discount <= 1): raise ValueError("discount 0-1")

# field(default_factory=) solves the mutable-default problem
@dataclass
class Cart:
    items: list[str] = field(default_factory=list)  # NOT default=[]

A classmethod receives the class (cls) as its first argument and can build instances of subclasses (polymorphic factory pattern). A staticmethod receives no implicit argument — it's just a regular function namespaced inside the class, used for utilities that logically belong there but don't need self or cls. The key design use: factory classmethods (@classmethod def from_json(cls, data)) replace telescoping constructors.

7 · The Iterator Protocol

What

Every for loop in Python calls two dunder methods under the hood: __iter__() on the container to get an iterator, then __next__() on the iterator repeatedly until it raises StopIteration. Any object implementing this two-method protocol is iterable — sets, dicts, files, database cursors, and your custom classes.

How — hand-written iterator vs generator
# Hand-written iterator: class with __iter__ and __next__
class Countdown:
    def __init__(self, start): self.n = start
    def __iter__(self): return self        # the iterator IS the object
    def __next__(self):
        if self.n <= 0: raise StopIteration
        self.n -= 1; return self.n + 1

assert list(Countdown(3)) == [3, 2, 1]

# Generator function: same result, zero boilerplate
def countdown(n):
    while n > 0:
        yield n; n -= 1

# built-in collections implement __iter__ returning dedicated iterator objects
mylist = [1, 2, 3]
it = iter(mylist)     # list_iterator
assert next(it) == 1  # consume one element
🔎
Why iterables and iterators are different objects

A container (like a list) returns a new iterator each time iter() is called, so you can iterate it multiple times independently. An iterator returns self from __iter__ — consuming it twice yields nothing the second time. This design lets for a in lst: for b in lst: produce the expected nested loops, not a one-pass mess.

8 · Generators & Lazy Evaluation

What

A generator is a function with yield. Each next() call runs the function until the next yield, produces its value, then suspends the entire stack frame (local variables, instruction pointer, everything) until the next call. This makes generators O(1) memory regardless of output length, and they can represent infinite sequences.

How — generators, infinite sequences, lazy pipelines
# Infinite generator — impossible with a list
def fibonacci():
    a, b = 0, 1
    while True:
        yield a; a, b = b, a + b

# Lazy pipeline — no intermediate lists created
def read_csv_rows(path):
    with open(path) as f:
        for line in f: yield line.strip().split(",")

pipeline = (
    row[2]
    for row in read_csv_rows("big.csv")    # step 1: read line by line
    if row[1] == "active"                   # step 2: filter
)
total = sum(float(v) for v in pipeline)   # step 3: aggregate — O(1) memory throughout

# itertools extends the lazy toolkit
import itertools
first_10_fibs = list(itertools.islice(fibonacci(), 10))
pairs = list(itertools.pairwise([1,2,3,4]))  # [(1,2),(2,3),(3,4)]

8a · yield from, send() & the Bridge to async/await

# yield from: delegate to a sub-generator — forwards send() and throw() transparently
def flatten(nested):
    for item in nested:
        if isinstance(item, list):
            yield from flatten(item)  # recursive delegation; not just yield
        else:
            yield item

assert list(flatten([1, [2, [3]], 4])) == [1, 2, 3, 4]

# send(): two-way communication — caller pushes a value INTO the generator
def running_total():
    total = 0
    while True:
        value = yield total    # suspend: yield current total, receive next value
        if value is None: break
        total += value

acc = running_total()
next(acc)         # prime: advance to first yield (must call next() first!)
acc.send(10)      # → yields 10
acc.send(5)       # → yields 15
💡
Why this matters: the bridge to async/await

async def / await are built directly on the generator protocol. An async def function is a coroutine; await expr is effectively yield from expr.__await__(). The event loop (asyncio) calls .send(None) on coroutines to advance them — exactly like the next(acc) call above. When a coroutine hits await asyncio.sleep(0), it yields control back to the event loop, which runs other coroutines, then resumes this one via send() when the awaitable completes. Understanding yield from and send() means you understand exactly why await suspends without blocking a thread — which is the heart of FastAPI's performance model.

When to choose generator over list

Choose a generator when: data is large (millions of rows), data is streamed (network, file), data is infinite (counter, Fibonacci), or you want natural back-pressure. Choose a list when: you need random access by index, need to iterate multiple times, or the sequence is small and code clarity benefits from materialization.

9 · Decorators — Cross-Cutting Concerns

What

A decorator is a callable that takes a function, wraps it, and returns the wrapper. The @decorator syntax is sugar for fn = decorator(fn). Decorators separate cross-cutting concerns (timing, retry, memoization, auth, logging) from the business logic they apply to — without touching the function's code.

How — decorator, parameterized decorator, class decorator
import functools, time

# Simple decorator: 1 level of nesting
def timed(fn):
    @functools.wraps(fn)               # preserves fn.__name__, fn.__doc__
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        result = fn(*args, **kwargs)
        wrapper.last_ms = (time.perf_counter() - t0) * 1000
        return result
    wrapper.last_ms = 0.0
    return wrapper

# Parameterized decorator: 3 levels of nesting (factory → decorator → wrapper)
def retry(times=3, exceptions=(Exception,)):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            last = None
            for _ in range(times):
                try: return fn(*args, **kwargs)
                except exceptions as e: last = e
            raise last
        return wrapper
    return decorator

@retry(times=3, exceptions=(ConnectionError,))
@timed
def fetch_data(url): ...    # retry is outer; timed is inner
⚠️
Gotcha — forgetting @functools.wraps

Without @functools.wraps(fn), fetch_data.__name__ returns "wrapper", docstrings vanish, and Sphinx/FastAPI/Pydantic generate broken documentation. Also, functools.lru_cache uses __qualname__ for its repr — wrapping without preserving identity produces confusing cache stats.

Q · What is a "decorator factory" and why does it have three levels of nesting?

A decorator factory is a function that returns a decorator. The three levels are: (1) the factory retry(times=3) — receives configuration; (2) the decorator decorator(fn) — receives the function to wrap; (3) the wrapper wrapper(*args, **kwargs) — replaces the original call. This is the general shape of app.route("/path"), @lru_cache(maxsize=128), and every configurable decorator in production frameworks.

9a · functools.lru_cache — production memoization

from functools import lru_cache, cache

# @lru_cache — memoize with bounded LRU eviction
@lru_cache(maxsize=128)
def fib(n: int) -> int:
    if n < 2: return n
    return fib(n-1) + fib(n-2)   # O(n) total calls, not O(2ⁿ)

# @cache (Python 3.9+) = lru_cache(maxsize=None) — unbounded
@cache
def expensive(key: str) -> object: ...

# Introspect and manage the cache
info = fib.cache_info()          # CacheInfo(hits=N, misses=M, maxsize=128, currsize=K)
fib.cache_clear()                # evict all — useful after config change
⚠️
Gotcha — lru_cache requires hashable arguments

lru_cache caches by hashing all positional and keyword arguments. Pass a list or dict and it raises TypeError: unhashable type. Fix: convert to tuple, or frozenset, or wrap in a hashable dataclass. Also: cached functions hold strong references to all cached return values — an unbounded @cache on a function returning large objects is a memory leak. Use maxsize to cap it.

10 · Advanced Dunder Methods — The Data Model

What

Python's data model (the dunder protocol) is the real interface system. Implement the right dunder methods and your objects participate in Python's built-in syntax — they print nicely, compare, sort, hash, iterate, index, manage resources, and call like functions. This is duck typing made formal: the protocol is real; the enforcement is yours.

How — value object, context manager, callable
from functools import total_ordering

@total_ordering
class Money:
    __slots__ = ("cents",)             # no __dict__ — saves memory
    def __init__(self, dollars):
        object.__setattr__(self, "cents", round(dollars * 100))
    def __repr__(self): return f"Money({self.cents/100:.2f})"
    def __eq__(self, o):  return isinstance(o, Money) and self.cents == o.cents
    def __hash__(self): return hash(self.cents)   # MUST match __eq__
    def __lt__(self, o):  return self.cents < o.cents   # @total_ordering derives <= > >=
    def __add__(self, o): return Money((self.cents + o.cents) / 100)

# Context manager: __exit__ returning False re-raises; True suppresses
class Transaction:
    def __enter__(self): self.log = ["BEGIN"]; return self
    def __exit__(self, exc_type, exc, tb):
        self.log.append("ROLLBACK" if exc_type else "COMMIT")
        return False    # do NOT suppress — re-raise the exception

# Callable instance: __call__ makes it behave like a function with state
class RateLimiter:
    def __init__(self, max_per_sec): self.rate = max_per_sec; self.tokens = max_per_sec
    def __call__(self): ... # check & decrement token bucket
💡
The __eq__/__hash__ contract — the most dangerous rule

The contract: objects that compare equal must hash equal (a == b ⇒ hash(a) == hash(b)). If you override __eq__ without __hash__, Python sets __hash__ = None (unhashable). Worse: define both inconsistently, or mutate a field used in hashing after insertion into a dict/set — the object lands in one bucket, its hash changes, and lookups return a miss while the entry still occupies memory. Silently lost data.

11 · Descriptors, __slots__ & Metaclasses

🧠 Mental model — descriptor lookup priority & __slots__

Attribute lookup order for obj.attr: (1) data descriptor in type(obj).__mro__ (has both __get__ and __set__/__delete__) → (2) obj.__dict__["attr"] → (3) non-data descriptor in type(obj).__mro__ (has only __get__) → (4) AttributeError. @property is a data descriptor — it always wins over the instance dict. Instance methods are non-data descriptors — the instance dict can shadow them (though rarely intentional). __slots__ memory model: a normal instance has a __dict__ hash table costing ~200 bytes overhead. A slotted instance uses a fixed C array (~56 bytes). For 1 million instances: ~200 MB vs ~56 MB. Trade-off: no dynamic attributes; subclasses must also declare __slots__ or the savings evaporate. Metaclass use: reach for __init_subclass__ first (90 % of cases), only use a full metaclass for framework-level hooks (__prepare__, ordering class attributes, Django/SQLAlchemy style).

What

Descriptors are objects with __get__/__set__/__delete__ that intercept attribute access. They are the machinery behind @property, methods, classmethod, staticmethod, and ORM fields. __slots__ replaces the per-instance __dict__ with a fixed set of fields, reducing memory and blocking attribute typos. Metaclasses are classes whose instances are themselves classes — they customize class creation.

How — descriptor, __slots__, metaclass
# Data descriptor: reusable validated field (DRY validation)
class Positive:
    def __set_name__(self, owner, name): self._name = "_" + name
    def __get__(self, obj, objtype=None):
        return self if obj is None else getattr(obj, self._name)
    def __set__(self, obj, value):
        if value <= 0: raise ValueError(f"{self._name[1:]} must be > 0")
        setattr(obj, self._name, value)

class Product:
    price    = Positive()    # one descriptor validates every Product.price assignment
    quantity = Positive()

# __slots__: fixed fields → no per-instance __dict__ → ~50% less memory
class Coord:
    __slots__ = ("x", "y")
    def __init__(self, x, y): self.x, self.y = x, y
# Coord().z = 1 → AttributeError: typo caught, not silently stored

# Metaclass: customize class creation (auto-registry pattern)
class PluginMeta(type):
    registry = {}
    def __new__(mcs, name, bases, ns):
        cls = super().__new__(mcs, name, bases, ns)
        if bases: PluginMeta.registry[name.lower()] = cls   # skip base class
        return cls

class Plugin(metaclass=PluginMeta): pass
class JsonExporter(Plugin): ...   # auto-registered as "jsonexporter" — zero boilerplate
🔎
When to use a descriptor vs @property

@property works per-class: if you need the same validation on 5 fields across 3 classes, you write it 15 times. A descriptor is a reusable object: write it once, assign it to any field in any class, and validation is DRY. ORM frameworks (SQLAlchemy, Django ORM) use descriptors for every column definition — that is why column = Column(Integer) validates on assignment without you writing any code.

11a · __init_subclass__ — lighter than a metaclass

What

__init_subclass__ (Python 3.6+) is called on a base class whenever a subclass is defined. It gives you the same "run at class creation" hook as a metaclass, but as a regular classmethod — simpler, cooperative with super(), and no metaclass machinery needed.

# Auto-registry via __init_subclass__ — zero boilerplate on the subclass
class Plugin:
    _registry: dict[str, type] = {}

    def __init_subclass__(cls, name: str = "", **kwargs):
        super().__init_subclass__(**kwargs)   # cooperative: pass kwargs up the MRO
        Plugin._registry[name or cls.__name__.lower()] = cls

class CsvPlugin(Plugin, name="csv"):   ...   # auto-registered — no decorator needed
class JsonPlugin(Plugin, name="json"): ...   # auto-registered
class XmlPlugin(Plugin): ...              # registered as "xmlplugin" (default name)

assert Plugin._registry["csv"] is CsvPlugin
__init_subclass__ (prefer)
Runs when subclass is defined · Simpler than metaclass · Keyword args from class header · Cooperative via super() · Python 3.6+ · No metaclass conflicts
Metaclass (when necessary)
Full control over the class dict before the class object exists · __prepare__ for custom namespaces · __class_getitem__ customization · Building DSLs or ORMs at framework level

12 · Typing, Protocols & Structural Interfaces

What

Python's type hints are transparent at runtime — they change no behavior. Their power is tooling (mypy, Pylance) and documentation. TypeVar and Generic express that a container's element type is flexible but consistent. Protocol provides structural typing: any class with the right methods satisfies the protocol, with no inheritance required.

How — TypeVar, Generic, Protocol, @contextmanager
from typing import Generic, TypeVar, Protocol
from contextlib import contextmanager, suppress

T = TypeVar("T")

class Stack(Generic[T]):                  # Stack[int] vs Stack[str] are distinct to mypy
    def __init__(self) -> None: self._items: list[T] = []
    def push(self, item: T) -> None: self._items.append(item)
    def pop(self) -> T: return self._items.pop()

class SupportsArea(Protocol):             # structural — no inheritance needed
    def area(self) -> float: ...

def total_area(shapes: list[SupportsArea]) -> float:
    return sum(s.area() for s in shapes)  # Circle or Square — no shared base

# @contextmanager: cleaner than a class for simple resource guards
@contextmanager
def db_transaction(conn):
    try:
        yield conn                        # bound to `as conn`
        conn.commit()
    except:
        conn.rollback(); raise            # re-raise so caller sees the error

with suppress(FileNotFoundError):        # named exception suppression — idiomatic
    old_file.unlink()
Q · When would you choose a Protocol over an ABC?

Choose Protocol when defining the shape of a dependency you consume, especially across module or package boundaries, or when you can't modify third-party types. The implementer needs no knowledge of your protocol — any existing class with the right methods just works, and test doubles are plain classes with no imports. Choose an ABC when you own the class family, need to share implementation in the base, or want an instantiation-time error rather than a type-checker error for incomplete implementations.

13 · The CPython Memory Model

What

CPython frees objects by reference counting: every object tracks how many names point at it and is freed immediately when that count reaches zero — no pause, deterministic. Reference counting has one blind spot: reference cycles (A → B → A) keep both counts above zero even when neither is reachable from user code. A cyclic garbage collector runs periodically to detect and reclaim such cycles. weakref lets you observe an object without contributing to its refcount.

How — inspecting refcounts, collecting cycles, building a leak-free cache
import sys, gc, weakref

# Refcount inspection
a = [1, 2, 3]
print(sys.getrefcount(a))   # +1 for the getrefcount call itself
b = a                       # refcount +1
del b                       # refcount -1 (immediate, no pause)

# Cycle: refcounting can NEVER free this without gc.collect()
class Node: pass
x, y = Node(), Node()
x.ref = y; y.ref = x        # cycle created
wx = weakref.ref(x)         # weak reference — does NOT keep x alive
del x, y
gc.collect()                 # cyclic GC breaks the cycle
assert wx() is None          # object is gone

# Leak-free cache with WeakValueDictionary
cache = weakref.WeakValueDictionary()
obj = SomeExpensiveObject()
cache["key"] = obj           # cache does NOT prevent GC
del obj                     # last strong owner gone
assert cache.get("key") is None   # auto-evicted — no manual cleanup needed
⚠️
Production trap — strong references in long-lived caches

Any long-lived dict (module-level cache, class variable) that stores objects by value holds a strong reference. If those objects have back-references to the cache (parent ↔ child, observer ↔ subject), you have a cycle that grows forever — a memory leak invisible to profiling tools that only look at active heap. The symptom is steady RSS growth that stops when you switch to WeakValueDictionary. Use weakref for caches and observer lists you don't intend to own.

Architect-Level Interview Bank
25 questions — from junior warm-up to staff-level deep dives
🎯

For each question: formulate your answer out loud before reading the model answer. The senior answer always names the trade-off, the failure mode, and the design rule — not just the mechanism.

Part A — Fundamentals (Junior → Mid)

Q1 · What is the difference between == and is? When is each correct? Junior

== calls __eq__ to compare values; is compares object identity (same address). Use == for values. Use is only for singletons: None, True, False. The trap: small ints (–5 to 256) and short strings are cached and interned, so is happens to work — until the value leaves that range and breaks silently.

Follow-up: "What is CPython's small-integer cache?" → CPython pre-allocates int objects for –5…256 at interpreter startup; names bound to those values all point at the same cached object. Implementation detail — never rely on it.
Q2 · Why does def f(x, cache={}) almost always misbehave? Junior

Default arguments are evaluated once at definition time and stored on f.__defaults__. Every call shares the same dict — accumulating state silently across callers. The fix is the sentinel idiom: def f(x, cache=None): if cache is None: cache = {}. The root cause is the object/reference model: the default is a reference, not a fresh allocation per call.

Q3 · Explain for…else. When is it actually useful? Junior

The else runs when the loop finishes without hitting break. Classic use: search loops. Without for/else you need a sentinel flag variable. With it: for item in candidates: if pred(item): result = item; break / else: result = default. Interviewers use this to probe whether you read the language reference or learned Python from Stack Overflow.

Q4 · list vs deque for a queue — which is faster and why? Junior

deque is faster for queue operations. list.pop(0) is O(n) because it shifts every remaining element left. deque.popleft() is O(1) — implemented as a doubly-linked list of blocks. For stacks (append/pop from the same end), both are O(1) and list is fine.

Q5 · What does EAFP mean and why does Python prefer it over LBYL? Junior

EAFP = Easier to Ask Forgiveness than Permission (try; catch the specific failure). LBYL = Look Before You Leap (check then act). EAFP is preferred because: (1) it avoids the TOCTOU race — a check and an operation are two steps; another thread can change state between them; (2) it's often faster — the "check" in LBYL duplicates work the operation does anyway; (3) it handles all failure modes, not just the ones you remembered to check. Python exceptions are cheap for the non-error path.

Part B — Intermediate (Mid → Senior)

Q6 · Is Python pass-by-value or pass-by-reference? Senior

Neither label fits. Python is call-by-object-reference (call-by-sharing). The function receives a reference to the same object — but the parameter name is a new binding. Mutation in-place (lst.append()) is visible to the caller because they share the object. Rebinding (lst = new_list) is local — the caller's binding is unaffected. Design rule: never mutate arguments you don't own; return new values instead, or document the mutation explicitly.

Q7 · Explain the __eq__/__hash__ contract. What breaks if you violate it? Senior

The contract: a == b ⇒ hash(a) == hash(b). Violation 1: override __eq__ without __hash__ → Python sets __hash__ = None (loud, immediate). Violation 2: define both inconsistently, or mutate a key after insertion. An object is placed in a dict bucket based on its hash. If the hash changes after insertion, lookups miss the bucket — the entry exists in memory but is unreachable. Silently lost data. That is why value objects must be effectively immutable for the fields that define equality.

Q8 · Generators vs lists for a 100M-row file stream — what changes? Senior

A list materializes all 100M rows: ~8–80 GB RAM depending on row size. A generator yields one row at a time: O(1) memory. Beyond memory: (1) latency — the first row arrives immediately vs after the whole file is read; (2) back-pressure — a slow downstream consumer automatically throttles I/O because nothing is produced until next() is called; (3) generators are single-pass and not indexable. In a pipeline, wrap with itertools.tee to fork — but that materializes internally, so if you need multiple passes, use a list or re-read the file.

Q9 · What is a decorator factory and why three levels of nesting? Senior

A decorator factory is a function that returns a decorator: retry(times=3) returns decorator; decorator(fn) returns wrapper; wrapper(*a, **kw) is the replacement call. Three levels because: level 1 captures configuration, level 2 captures the function, level 3 intercepts every call. This is the shape of @app.route("/path"), @lru_cache(maxsize=128), and every configurable framework decorator. Forgetting @functools.wraps at level 3 erases the function's identity — a silent documentation and introspection bug.

Q10 · Explain the LEGB rule and the late-binding closure trap. Senior

LEGB: name lookup goes Local → Enclosing (closure) → Global (module) → Built-in. A closure captures the variable, not its value — so lambdas = [lambda: i for i in range(3)] all reference the same loop variable i. When called after the loop, i is 2 for all three. Fix: bind the current value as a default: lambda i=i: i. This creates a new local scope on each iteration, capturing the current value. Same root cause as the mutable-default trap: closures close over variables, not values.

Part C — Advanced / Staff Level

Q11 · Explain the CPython memory model. When is weakref the right tool? Staff

CPython frees objects by reference counting: immediate at count zero, no GC pause. Blind spot: reference cycles (A → B → A) keep refcounts above zero; the cyclic GC reclaims them periodically (every ~700 allocations by default). weakref is the right tool when you want to observe an object without owning it: caches (WeakValueDictionary auto-evicts entries when the real owner is gone), observer/event patterns (subjects don't keep listeners alive indefinitely), and parent↔child back-references. Use regular references where ownership is intended; use weakref where it isn't.

Follow-up: "How would you detect a reference-cycle leak in production?" → use gc.get_unreachable(), objgraph, or memory-profiler; look for growing RSS with stable heap — often a module-level dict holding closures that captured large objects.
Q12 · How does CPython implement @property? What is a descriptor? Staff

@property is a data descriptor — an object with __get__ and __set__. Python's attribute lookup gives data descriptors priority over instance __dict__. So obj.x = 5 calls property.__set__(obj, 5), not obj.__dict__["x"] = 5. This is why @property can validate, compute, or delegate on both get and set. A descriptor is reusable: one Positive() class validates every field it's assigned to, across every class — the DRY validation pattern that ORM column definitions use (SQLAlchemy's Column() is a descriptor).

Q13 · Protocol vs ABC — when does each apply? Staff

The axis is coupling. A Protocol is structural: any class with the right shape satisfies it, zero coupling, no imports. An ABC is nominal: membership requires explicit inheritance. Use Protocol when consuming an interface across a boundary (especially third-party or test doubles) — it embodies Dependency Inversion without an inheritance tree. Use ABC when you own the class hierarchy, need to share implementation in the base, or want instantiation-time (not type-check-time) enforcement. The senior phrasing: "Protocol for what I consume; ABC for what I own."

Q14 · What are metaclasses and when should you use one vs a class decorator? Staff

A metaclass is a class whose instances are classes — it customizes class creation (runs at class statement time). A class decorator wraps a class after creation. Use a metaclass when: (1) every subclass must be automatically registered or modified; (2) you need to enforce constraints at class-definition time (before any instance exists); (3) building DSLs or ORMs (Django models use metaclasses to collect field descriptors). Use a class decorator when the modification is simpler, applies to a specific class (not all subclasses), or you want explicit opt-in. Metaclasses are powerful but add invisible complexity — the Python docs say "if in doubt, you don't need one."

Q15 · You have a hot path creating millions of small objects per second. How do you reduce memory overhead? Staff

Three graduated approaches: (1) __slots__ — remove per-instance __dict__ (saves 56–200 bytes per instance depending on fields); (2) dataclass(slots=True) (Python 3.10+) — automatic slot generation with dataclass ergonomics; (3) numpy structured arrays / Cython / Rust extension — for true zero-overhead memory layout. Measure first with sys.getsizeof() and tracemalloc. Profile before optimizing — premature slot-ification costs flexibility (subclassing becomes harder, dynamic attributes are blocked).

Part D — Architecture Connection Questions

Q16 · A FastAPI endpoint processes 10K requests/sec. Each request creates a Pydantic model. What Python primitives underpin Pydantic's validation? Staff

Pydantic v2 uses descriptors for field definitions and __init_subclass__ / metaclass machinery to introspect type annotations at class-definition time. At runtime, validators are effectively __set__ descriptors. The Python connection: type hints power schema introspection; __slots__ (in v2 models) reduces per-model memory; Protocol is how BaseSettings providers are typed. Every Python feature in this book is load-bearing in the framework.

Q17 · Describe three ways generators provide back-pressure in a streaming pipeline. Staff

(1) Lazy pull model: the consumer drives production via next(); a slow consumer simply doesn't call next() and the producer stays suspended. (2) Backpressure across I/O: a generator reading from a socket reads only what the consumer has requested — no unbounded buffering. (3) asyncio.Queue with maxsize: combine async generators with a bounded queue — await queue.put() blocks the producer coroutine when the queue is full, creating explicit flow control. Without generators, you'd need manual buffer management or a streaming library.

Q18 · An observability system stores 50K live Event objects. Each holds a strong reference back to its parent Span. After 90% of events are done, memory doesn't drop. Diagnose. Staff

Classic reference-cycle memory leak. Event ↔ Span forms a cycle that reference counting alone cannot break (each object keeps the other's refcount above zero). Even after user code discards all names pointing at them, the cycle persists until gc.collect() runs. Diagnosis steps: (1) gc.get_count() — if generation 2 is growing, cycles are accumulating; (2) objgraph.show_most_common_types() — confirms Event/Span are the culprits; (3) Fix: replace back-references with weakref.ref(parent) — the cycle is broken, refcounting reclaims objects immediately. Also consider gc.collect() at request boundaries for predictable latency.

Q19 · What does yield from do that a plain for/yield loop cannot? Staff

Three things a manual loop cannot do: (1) forwards .send(value) to the sub-generator — the value arrives at the sub-generator's yield expression; (2) forwards .throw(exc) into the sub-generator; (3) captures the sub-generator's return value as the expression's result. These three are essential for coroutine chains — when the event loop send()s a result to resume a coroutine, yield from passes it through every layer of the async call stack. This is the mechanical foundation of await.

Q20 · How does nonlocal differ from just mutating a captured mutable object? Senior

Mutating a captured mutable object (lst.append(x)) requires no declaration — you're calling a method through an existing reference, no rebinding occurs. count += 1 desugars to count = count + 1, which is an assignment. Python's compiler treats any assigned name in a function as local at compile time — without nonlocal, Python sees an uninitialized local count on the right side and raises UnboundLocalError. Design rule: prefer returning new values over nonlocal mutation — closures with mutable state are harder to reason about than pure functions.

Q21 · When should you use raise X from Y vs raise X from None? Senior

raise DomainError(...) from original sets __cause__ and shows both exceptions in the traceback — use when the original cause is useful for debugging (translating a library exception to a domain exception). raise DomainError(...) from None suppresses the context — use when the original is an implementation detail callers shouldn't depend on (KeyError → CacheMiss). Never use a bare raise NewError inside an except — it chains implicitly via __context__ and may expose internal details.

Q22 · When is @dataclass(frozen=True, slots=True) the right choice? Senior

Use frozen for immutable value objects (Money, Coordinate, Config) — auto-generates __hash__, making instances safe as dict keys and thread-safe. Use slots when instantiating at high frequency (10K+/sec) — removes __dict__ overhead (~50% memory saving, faster attribute access). Combined: event objects in event-sourcing systems (immutable, millions created), request DTOs in high-throughput APIs. Caveats: frozen blocks assignment post-init (use object.__setattr__ in __post_init__ for computed fields); slots complicates subclassing; both require Python 3.10+ for slots=True.

Q23 · How would you design a plugin registry without a metaclass? Staff

Three options by coupling level: (1) __init_subclass__ — subclasses auto-register via keyword args at class-definition time; cooperative, zero boilerplate, stays in-process. (2) Class decorator — @register is explicit opt-in; clear, auditable, no magic. (3) Entry points (importlib.metadata) — plugin installed as a separate package, no import coupling, most scalable for third-party ecosystem. Choose based on coupling tolerance: __init_subclass__ for in-repo plugins; entry points for external ecosystem plugins.

Q24 · Your service creates 5M Point(x, y) objects per minute and memory is climbing. Walk through your optimization strategy. Staff

In order: (1) Measure first: sys.getsizeof(Point(0,0)) and tracemalloc to confirm Point instances are the culprit. (2) @dataclass(slots=True) — no code change at call sites, removes __dict__, typically halves instance size. (3) Measure again — confirm the saving. (4) If still insufficient: numpy structured array — contiguous C-array, 8 bytes per point vs 200+ for a Python object. Never optimize before measuring; never optimize the wrong thing.

Q25 · Design a type-safe event bus in Python. What features would you use and why? Staff

(1) Generic[T] + Protocol — Handler[E] is structurally typed with def handle(self, event: E) -> None; any class with that signature satisfies it without inheritance. (2) Decorator factory — @bus.on(OrderPlaced) registers a handler; internally stores {type: [callable]}. (3) dataclass(frozen=True) for events — immutable, hashable, safe across threads. (4) TypeVar bound — E = TypeVar("E", bound=BaseEvent) ensures end-to-end type safety. (5) WeakValueDictionary (or weakref.ref) for handlers — prevents the bus from keeping handler objects alive after their owners are garbage-collected. Result: ~30 lines of type-checked, memory-safe Python.

Part F — Gotchas Checklist

🏁 Before your next Python interview — verify you can explain all of these
  • Mutable default arguments (def f(x, a=[])) are shared — always use None sentinel.
  • Aliasing: b = a on a mutable object means mutations through b are visible through a.
  • __eq__ without __hash__ → unhashable; both inconsistently → silent dict/set corruption.
  • Generators are single-pass and not indexable; consuming twice yields nothing the second time.
  • Generator errors surface lazily — the exception appears when the item is pulled, not when the generator is created.
  • Forget @functools.wraps → decorator erases __name__, __doc__, and __module__.
  • Late-binding closures in loops: lambda: i captures variable, not current value — use lambda i=i: i.
  • __exit__ returning truthy swallows exceptions — almost always wrong in production code.
  • Reference cycles + strong caches = memory leak; use weakref.WeakValueDictionary for caches you don't own.
  • Type hints are transparent at runtime — they don't validate; use Pydantic at system boundaries.
  • super() follows the MRO; hard-coding Parent.method(self) breaks cooperative multiple inheritance.
  • __slots__ is an optimization — apply it only where the memory profile justifies the lost flexibility.
  • Metaclasses run at class-definition time, not at instantiation — unexpected behavior if you put I/O in them.
