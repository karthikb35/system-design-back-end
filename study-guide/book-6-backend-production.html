Production is where "works on my machine" goes to die

Almost every incident in this book has the same shape: code that is correct for one request on one machine with a fast dependency, that breaks when there are thousands of concurrent requests, a slow replica, or a partial failure. Senior engineering is designing for the concurrent, failing, observable case from the start — and being able to prove it with a number.

1 · The FastAPI Event Loop

What

FastAPI runs async def routes on a single-threaded event loop. The loop serves many requests concurrently by switching between them whenever one awaits I/O. A blocking call — time.sleep, a synchronous DB driver, requests, heavy CPU — inside an async route holds the loop and stalls every other request.

Why it matters

Because this is the number-one FastAPI production footgun, and it's invisible in local testing where you send one request at a time. Under concurrency the throughput collapses: while one route blocks, not even a trivial /health can respond. The fix is to either await genuinely-async I/O, offload the blocking work to a threadpool, or make the route a plain def.

How — the refactor
# ❌ freezes the loop for EVERYONE while it sleeps
@app.get("/junior/report")
async def report_junior():
    result = _blocking_io()                      # blocking call in async route
    return {"result": result}

# ✅ offload the blocking call so the loop keeps serving others
@app.get("/senior/report")
async def report_senior():
    result = await run_in_threadpool(_blocking_io)
    return {"result": result}
⚠️
Gotcha — a plain def route is safe; an async def with blocking I/O is not

Counter-intuitively, if your route must do blocking work, a synchronous def route is safer than an async def one: FastAPI automatically runs def routes in a threadpool, so they don't block the loop. The danger is specifically blocking work inside async def. Rule of thumb: if you can't await it, either offload it or make the route def.

Q · Why does a blocking call in an async def route hurt so much?

Async routes share one event loop thread. The loop only switches tasks at await points, so a blocking call (no await) holds the thread for its full duration, during which no other request — including health checks — can run. It looks fine under single-request testing and collapses under concurrency. Fix by awaiting async I/O, offloading to a threadpool, or using a def route.

Q · When would you deliberately use a synchronous def route?

When the work is inherently blocking (a sync DB driver, a CPU-bound computation, a legacy library with no async API). FastAPI runs def routes in a threadpool automatically, keeping the event loop free. Reserve async def for routes that actually await async I/O end-to-end.

2 · API Design at Scale

What

The contract your service exposes: request validation (Pydantic models at the boundary), pagination (how clients page through large result sets), versioning (evolving without breaking clients), and idempotency (safe retries for writes). The headline decision at scale is offset vs cursor (keyset) pagination.

Why it matters

Because LIMIT ? OFFSET ? pagination degrades the deeper clients page — the database must scan and discard every skipped row — and it can skip or duplicate rows when data changes between requests. Cursor pagination (WHERE id > last_seen) does constant work per page and returns stable results. On a large table this is a 1000× difference, measured in the companion script.

PaginationDeep-page costStabilityRandom access
Offset (LIMIT/OFFSET)O(offset) — scans skipped rowsskips/dupes on insertyes ("go to page 50")
Cursor / keysetO(limit) — constantstableno (next/prev only)
How — keyset beats offset
# ❌ OFFSET: the DB scans and throws away every skipped row
SELECT * FROM items ORDER BY id LIMIT 20 OFFSET 180000;   # scans 180,020

# ✅ KEYSET: seek straight to the cursor via the index
SELECT * FROM items WHERE id > 180000 ORDER BY id LIMIT 20;   # touches 20
📂 Measured in the repo
  • 05-fastapi-advanced/examples/pagination.py — deep page: OFFSET scans 180,020 rows for 20 results; KEYSET touches 20 (~9000× cheaper), and keyset stays O(limit) per page at any depth.
⚠️
Gotcha — validate at the boundary, and cap the page size

Trust nothing from the client. Use a Pydantic model to validate and coerce input at the edge, and always cap limit (e.g., max 100) — otherwise a client asking for limit=10000000 can OOM your service or melt the database. Reject early with a 422, before any business logic runs.

Q · Offset vs cursor pagination — when each?

Cursor (keyset) for large datasets and infinite-scroll feeds: constant cost per page and stable under concurrent inserts, but no random page jumps. Offset for small/bounded datasets or admin UIs that need "jump to page N," accepting that deep pages get slow and results can shift. Most high-scale public APIs use cursors.

Q · How do you version an API without breaking clients?

Prefer additive, backward-compatible changes (new optional fields, new endpoints) so existing clients keep working. For breaking changes, version explicitly (URL path /v2/… or a header), run old and new side by side during migration, and deprecate on a published timeline. Never repurpose or remove an existing field's meaning in place.

3 · Resilient Service Calls

What

The discipline of calling other services safely: a timeout on every call (never wait forever), bounded retries with exponential backoff + jitter, and a circuit breaker that stops calling a dependency that's clearly down. Together they turn "a dependency is struggling" into "we degrade gracefully" instead of "we amplify the outage."

Why it matters

Because naive retries are how a small blip becomes a full outage. When a service slows, clients retrying immediately multiply the load — a retry storm that keeps the struggling dependency down. Backoff+jitter spaces retries out; a circuit breaker gives a dead dependency room to recover instead of pounding it.

⚠️
Gotcha — retries without jitter synchronize the storm

Even with exponential backoff, if every client uses the same delays they all retry at the same instants — synchronized waves that keep hammering the dependency. Full jitter (a random delay between 0 and the backoff ceiling) spreads retries out so the load smooths. Also cap total attempts and pair with a circuit breaker so you stop retrying a dependency that's truly down.

🔎
Timeouts are non-negotiable

Every network call needs a timeout — without one, a hung dependency ties up your workers/connections until you run out and go down too. Set timeouts shorter than your own SLA, budget them across a call chain (the total must fit your deadline), and treat a timeout as a failure that feeds the retry/breaker logic.

Q · What is a retry storm and how do you prevent it?

When a dependency slows, clients retry immediately and multiply its load, keeping it down — a self-amplifying outage. Prevent it with exponential backoff + full jitter (spaced, desynchronized retries), a capped attempt count / retry budget, and a circuit breaker that fails fast once the dependency is clearly unhealthy, giving it room to recover.

Q · Which requests are safe to retry?

Idempotent ones — where repeating has the same effect as doing it once (GETs, PUTs, deletes, or writes guarded by an idempotency key). Retrying a non-idempotent write (a bare "charge card") risks duplicate side effects. Make writes idempotent (idempotency keys) before enabling retries on them.

4 · Talking to the Database

What

The mechanics of accessing data correctly: avoiding the N+1 query (one query for a list, then one per row), reusing connections through a pool instead of opening one per request, wrapping related writes in a transaction, and adding indexes to turn full-table scans into seeks.

Why it matters

Because the database is almost always the first thing to fall over, and the causes are boringly consistent: an ORM lazily firing 200 queries to render one page, connections leaked until the DB refuses new ones, and a missing index turning a 1ms lookup into a 500ms scan. These are invisible on a laptop with 10 rows and fatal at production scale.

📂 Runnable in the repo
  • 07-database-scaling/production_code.py — counts queries: N+1 fires 1+N; the batched/joined version fires O(1).
  • 07-database-scaling/examples/connection_pool.py — 100 requests served by 3 pooled connections; leak-safe even on error; exhaustion detected.
⚠️
Gotcha — the connection leak & the "too many connections" outage

Forget to return a connection on an error path and it's leaked; enough leaks and the pool empties, every request hangs waiting, and the app is down — even though the database is healthy. The fix is to acquire connections through a context manager that always releases in a finally, and to bound the pool so a slow query can't open unlimited connections.

Q · What is the N+1 query problem and how do you fix it?

Fetching a list (1 query) and then a related record per row (N queries) yields 1+N round-trips, so latency grows with result size. Fix it by fetching related data in one go: a JOIN, an eager-load/prefetch (e.g. selectinload), or an IN (...) batch. The round-trip count should be constant regardless of row count.

Q · Why pool database connections?

Opening a connection is expensive (TCP + auth handshake), and databases cap concurrent connections. A pool opens a bounded set once and reuses them across requests, cutting latency and protecting the DB's connection limit. The critical discipline is always returning connections (context managers) so leaks don't exhaust the pool.

5 · Scaling the Data Tier

What

Growing the database past one node: read replicas (copies that serve reads), read/write routing (writes to the primary, reads to replicas), sharding (splitting data across nodes), and safe schema migrations (evolving structure without downtime). This is Book V's replication/partitioning theory, made concrete in an app.

Why it matters

Because a single primary eventually caps out on read throughput, then on write throughput and storage. Read replicas offload the (usually dominant) read traffic; sharding scales writes and capacity. But each adds a failure mode — replication lag causing stale reads, cross-shard queries, and migrations that lock tables — that you must design around.

How — route reads to replicas, writes to the primary
async def get_session(readonly: bool = False):
    return replica_session() if readonly else primary_session()

@app.get("/orders")          # reads -> replica (spares the primary)
async def list_orders(db = Depends(lambda: get_session(readonly=True))): ...

@app.post("/orders")         # writes -> primary
async def place_order(db = Depends(get_session)): ...
⚠️
Gotcha — replication lag breaks "read your own writes"

Route a read to a replica right after a write and the user may not see their own change (the replica hasn't caught up). Fix by routing a user's reads to the primary for a short window after they write, or by tracking a write token and reading from a replica that's caught up to it. Never assume a replica is current.

⚠️
Gotcha — the migration that locked the table

Adding a column with a default, or an index, on a large table can hold a lock long enough to stall every write — an outage during a routine deploy. Use online/concurrent DDL, add columns nullable-then-backfill in batches, and split destructive changes into expand → migrate → contract phases so old and new code both work during the rollout.

Q · How do read replicas help, and what's the catch?

They serve read traffic (usually the majority), offloading the primary so it can focus on writes, and add redundancy. The catch is replication lag: replicas are slightly behind, so reads can be stale — problematic for read-your-writes. Route latency-tolerant reads to replicas and consistency-critical reads (or a user's own recent writes) to the primary.

Q · How do you run a schema migration with zero downtime?

Use the expand/contract pattern: first make additive, backward-compatible changes (add nullable columns/tables) so old and new code coexist; deploy code that writes both old and new; backfill data in batches; switch reads to the new shape; then contract by removing the old columns once nothing uses them. Avoid long-locking DDL on big tables.

6 · Reliable Writes & Events

What

Making a write and its side effect (an event, an email, an update to another service) reliable. The core hazard is the dual-write problem: you can't atomically write to a database and a message broker. The standard fix is the transactional outbox — write the business row and an outbox row in one DB transaction, then a relay publishes the outbox.

Why it matters

Because "save the order, then publish OrderPlaced" is two systems with no shared transaction: crash in between and you get an order with no event (downstream never hears) or an event with no order (a phantom). At scale this happens constantly, and the inconsistencies are silent and permanent until a customer complains.

🔎
At-least-once + idempotent consumers = exactly-once effect

The relay marks a row sent after publishing, so a crash in between re-sends it — delivery is at-least-once, never lost. The duplicates are handled on the consumer side: dedupe by event id so processing the same event twice has the same effect as once. "Exactly-once delivery" is largely a myth; "exactly-once effect" via idempotency is the achievable goal.

Q · What is the dual-write problem?

Writing to two systems that can't share a transaction — e.g., a database and a message broker — with no atomicity between them. A crash after the first write and before the second leaves them inconsistent (an order without its event, or vice versa). The transactional outbox solves it by writing the business change and the event to the same database in one transaction, then relaying the event separately.

Q · How does the transactional outbox guarantee delivery?

The event is stored as an outbox row inside the same DB transaction as the business write, so it's durable and atomic with the change. A relay/poller then reads unsent rows and publishes them, marking each sent only after a successful publish. If it crashes mid-way it re-publishes on restart (at-least-once), so no event is lost; consumers dedupe to absorb duplicates.

7 · Observability

What

The ability to understand what your system is doing from the outside, via three pillars: logs (structured, searchable events), metrics (aggregated numbers over time — the RED method: Rate, Errors, Duration), and traces (one request's path across services). A correlation ID stitches all a request's logs together; the ELK/OpenSearch stack aggregates and searches them.

Why it matters

Because when production breaks at 3 a.m., you can only fix what you can see. print(f"user {u} did {x}") is unsearchable, has no request id, and leaks secrets. Structured JSON logs with a correlation id let you filter to a single failing request across every service; RED metrics tell you which endpoint is on fire; traces show where the time went.

  • 06-elk-monitoring/production_code.py — a correlation-id middleware (contextvar) + JSON logging.
  • 06-elk-monitoring/examples/structured_logging.py — JSON logs, per-request correlation, secret redaction, and RED metrics (rate/errors/p95).
  • 06-elk-monitoring/docker-compose.yml, logstash/, filebeat/ — a real ELK pipeline to run locally.
⚠️
Gotcha — logging secrets and PII

Dumping request bodies or headers into logs happily records passwords, tokens, and card numbers — a compliance breach sitting in your log store forever. Redact known-sensitive fields at the logging boundary (allowlist what to log, or denylist secrets), never log full auth headers, and scrub PII. The structured_logging.py example redacts password/token/secret/card automatically.

🔎
Alert on symptoms (SLOs), not causes

Page humans for what users feel — error rate and latency breaching an SLO — not for every CPU spike or single failed request (that's alert fatigue). Use the RED/golden signals for alerting, keep detailed logs and traces for diagnosis after the page, and make every alert actionable. A good alert answers "users are being hurt, right now."

Q · Why structured logging over plain strings?

Structured logs (JSON with named fields) are machine-parseable, so a log platform can filter, aggregate, and alert on them (event="request.failed" AND status=500). Plain f-string logs are only human-readable and nearly impossible to query at scale. Structure also lets you attach a correlation id to every line and redact sensitive fields consistently.

Q · Logs vs metrics vs traces — when do you reach for each?

Metrics first: they tell you something is wrong and how bad (error rate/latency by endpoint). Traces next: they show where in a request's cross-service path the time or failure is. Logs last: the detailed record of what happened for a specific request, found via its correlation id. Together they take you from "alarm" to "root cause."

8 · Event-Driven Systems & Kafka

What

Decoupling services with a durable log-based broker (Kafka). Producers append events to topics split into partitions; consumers track their position with offsets and can replay. Because delivery is at-least-once, consumers must be idempotent; cross-service workflows use the saga pattern instead of distributed transactions.

Why it matters

Because synchronous chaining ("place order" calls inventory, then email, then analytics inline) couples availability and latency — if email is slow, order placement is slow; if analytics is down, orders fail. Publishing an OrderPlaced event lets independent consumers react on their own schedule, absorbing spikes and letting you add consumers without touching the producer.

⚠️
Gotcha — the poison message that stalls the partition

Kafka preserves order within a partition, so a single event a consumer can never process (a "poison message") can block every event behind it — the partition wedges. The fix is a dead-letter queue: after N failed attempts, move the message aside so the partition keeps flowing, and investigate the DLQ separately. The idempotent_consumer.py example includes one.

🔎
Sagas replace distributed transactions

You can't wrap "reserve inventory → charge card → create shipment" in one ACID transaction across services. A saga runs them as a sequence of local transactions; if a later step fails, it invokes compensating actions (refund the card, release the inventory) in reverse to undo the earlier ones. It trades atomicity for eventual consistency plus explicit rollback logic — see saga.py.

🧠
Backpressure — matching producer speed to consumer capacity

What: Backpressure is resistance applied upstream when downstream can't keep up. Without it, a fast producer overflows the consumer's queue → unbounded memory growth → OOM crash. The strategies, ranked by data-safety:

StrategyMechanismSafe for payments?
BlockProducer blocks when queue full; delay propagates upstream✓ Yes — no data loss
DropReject new items at capacity; fast, bounded memory✗ Never — data lost
SampleAccept 1-in-N; preserves statistical shape✗ Never — for metrics/telemetry only
Scale outAutoscale consumers (HPA on queue depth)✓ Yes — but has autoscale lag

Gotcha: unbounded queues hide backpressure entirely — the app runs fine until it hits OOM and crashes. Always set an explicit bound. In asyncio, use asyncio.Queue(maxsize=N) with await q.put(); the blocking queue.Queue blocks the event loop thread. Runnable in 04-system-design/examples/connection_pool_backpressure_idempotency_dlq.ipynb.

Q · Why must Kafka consumers be idempotent?

Because Kafka guarantees at-least-once delivery: after a consumer processes a message but before it commits its offset, a crash or rebalance re-delivers that message. If processing isn't idempotent, the effect happens twice (double charge, duplicate row). Deduping by a stable event id (or using upserts / natural idempotency) makes redelivery harmless — an exactly-once effect.

Q · What does a saga do when a step fails?

It runs compensating transactions for the steps already completed, in reverse order, to semantically undo them (e.g., refund a payment, release a reservation) — since you can't roll back committed local transactions across services. The system reaches a consistent state through explicit compensation rather than a distributed rollback, accepting eventual consistency in between.

9 · Deployment & Operations

What

Getting the service running reliably in production: packaging it in a container, exposing health checks (liveness/readiness), managing config & secrets via the environment, and rolling out new versions with zero downtime (rolling/blue-green/canary).

Why it matters

Because the best code is worthless if deploys cause outages, secrets are baked into images, or a crashed process never restarts. Containers make "works on my machine" reproducible; health checks let the orchestrator route around sick instances; environment config keeps secrets out of the codebase; and progressive rollouts catch a bad release before it hits everyone.

RolloutHowTrade-off
Rollingreplace instances a few at a timesimple; mixed versions run together
Blue-greenstand up new fleet, flip traffic at onceinstant rollback; double the infra briefly
Canarysend a small % to the new version firstcatches bad releases early; more orchestration
⚠️
Gotcha — secrets in the image or the repo

Hard-coding an API key in the code or a Dockerfile bakes it into every image layer and every git clone — permanently, even after you "delete" it. Inject secrets at runtime from the environment or a secrets manager, keep .env out of version control (see 06-elk-monitoring/.env.example as the committed template), and rotate anything that ever leaked.

🔎
Liveness vs readiness — they answer different questions

Liveness: "is the process wedged and in need of a restart?" (fail → kill & restart). Readiness: "can it serve traffic right now?" (fail → stop routing to it, but don't restart). Conflating them is a classic outage: a slow dependency makes readiness fail, but if it's wired as liveness the orchestrator restarts healthy pods in a loop. Keep them separate.

Q · Liveness vs readiness probes?

Liveness detects a hung process that needs restarting; failing it triggers a restart. Readiness detects whether an instance can currently serve requests (dependencies up, warmup done); failing it removes the instance from the load balancer without restarting. Use readiness for transient "not ready yet" states and liveness only for truly unrecoverable ones.

Q · How do you deploy without downtime?

Roll out progressively (rolling/canary/blue-green) behind health checks so traffic only goes to ready instances, and keep changes backward-compatible so old and new versions coexist during the rollout (especially DB schema — expand/contract). Drain in-flight requests on shutdown (graceful termination) and keep rollback fast (blue-green or a previous image) for when a release misbehaves.

10 · The Production Readiness Checklist

What

The set of properties a service needs before it carries real traffic and a pager: defined SLOs, graceful shutdown, load shedding, capacity headroom, runbooks, and alerts. It's the difference between "it runs" and "it's operable."

Why it matters

Because production readiness isn't a feature you add later — it's the acceptance criteria for shipping. A service without graceful shutdown drops in-flight requests on every deploy; one without load shedding falls over completely under overload instead of degrading; one without SLOs has no shared definition of "healthy" to alert on.

🔎
Graceful shutdown & load shedding

Graceful shutdown: on SIGTERM, stop accepting new requests, finish in-flight ones (up to a deadline), close DB/broker connections, then exit — so a deploy doesn't drop live traffic. Load shedding: when overloaded, reject some requests fast (429) to protect the rest, rather than slowing to a crawl for everyone and collapsing. Both are about failing partially instead of totally.

🧠
SLIs, SLOs, and the error budget

An SLI is a measured signal (e.g., % of requests under 200ms). An SLO is the target for it (99.9%). The gap between the SLO and 100% is your error budget — the amount of unreliability you're allowed to spend. It reframes reliability as a budget: if you're within budget, ship features faster; if you've blown it, stop and stabilize. It aligns product speed with reliability instead of pitting them against each other.

Q · What is an error budget and how do teams use it?

It's 1 − SLO — the allowed amount of failure over a window (e.g., 0.1% of requests may miss the latency target). Teams use it as a control knob: with budget remaining, they ship changes aggressively; once it's exhausted, they freeze features and focus on reliability. It turns "how reliable is reliable enough?" into a shared, data-driven decision.

Q · What happens to in-flight requests during a deploy?

With graceful shutdown, the instance stops accepting new requests on SIGTERM, finishes in-flight ones up to a timeout, closes connections cleanly, then exits — so no live request is dropped. Without it, the process is killed mid-request and clients see errors on every rollout. Orchestrators also stop routing new traffic (readiness/pre-stop hooks) before termination to drain cleanly.

🎯 Key takeaways
  • Never block the event loop — offload blocking work to a threadpool or use a def route.
  • Cursor over offset pagination at scale — constant work per page, stable results.
  • Every remote call needs a timeout, bounded retries with backoff+jitter, and a circuit breaker.
  • Kill the N+1 with joins/batching; pool connections and always release them.
  • Route reads to replicas, writes to the primary — and design around replication lag.
  • Solve dual-writes with the transactional outbox; make consumers idempotent for at-least-once.
  • Observe with structured logs + correlation IDs + RED metrics + traces; alert on SLOs, redact secrets.
  • Event-driven decouples — Kafka partitions/offsets, idempotent consumers, DLQs, and sagas for workflows.
  • Apply backpressure explicitly: bound all queues; block (not drop) for correctness-critical work; autoscale consumers on queue depth.
  • Deploy safely: containers, split liveness/readiness, secrets from the environment, graceful shutdown, progressive rollouts.
  • Every pathology here is runnable in pillars 05–08 — measure it, break it, fix it.
